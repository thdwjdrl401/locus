# 0002 — 모듈 구조: 단일 모듈 + ArchUnit

- 상태: 확정
- 일자: 2026-06-19

## 결정
**멀티모듈을 쓰지 않는다.** 단일 Gradle 모듈로 가고, `core`가 인프라에 의존하지 못하도록
**ArchUnit 테스트**(`CoreIsolationTest`)로 경계를 빌드 단에서 강제한다.

## 맥락 / 논의 경과
멀티모듈을 진지하게 검토했다. 멀티모듈의 이 프로젝트 내 유일한 실질 이득은
*"M3·M9의 'core 변경 0줄'을 컴파일 단으로 강제"* 인데, 따져보니 약했다.

- 추상화 증명("이 PR에서 `core`는 diff에 안 떴다")은 모듈이 아니라 **패키지 경계 + PR diff**로 충분히 보인다.
- 그 컴파일 강제는 **ArchUnit 한 테스트로 대체**된다. 아키텍처 규칙을 테스트로 코드화해 CI에서 검증하는 편이 더 견고하고 자동화된다.
- 측정 격리(시뮬레이터 JVM 분리) 논리도 약하다. **부하 주력은 k6**(별도 프로세스)라 M1 측정은 이미 외부에서 해결된다.
- 무엇보다 **모듈 구조는 이 프로젝트의 본질이 아니다.** 본질은 수집·부하·적재(M0~M2)이고, 모듈 나누기로 M0 시작을 늦추는 건 우선순위 역전이다.

## 기각된 대안
- **풀 4모듈**(core/device-types/app/simulator): 과함. 부수적 구조에 초기 설정 비용을 지불.
- **2모듈**(core + 나머지): 컴파일 강제는 살지만, ArchUnit이면 비용 없이 같은 효과.

## 영향
- 경계 위반 시 `./gradlew test`가 실패한다(빌드 게이트).
- 업그레이드 경로 유지: 패키지 경계를 깔끔히 지키면 나중에 `core`를 모듈로 추출하는 건 소규모 작업.

## 후속
- ArchUnit 규칙은 `core` 외에도 슬라이스 간 의존 규칙으로 확장 가능(필요 시).
