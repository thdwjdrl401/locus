# 아키텍처 리스크 등록부

수집 파이프라인의 **알려진 구조적 리스크**를 한곳에 모은다. 문서 역할 구분:
- `docs/decisions/`(ADR) = *내린 결정*, ROADMAP "보류된 결정" = *의도적으로 미룬 결정*, **이 문서 = 아직 열려 있는 위험**.
- **상태**: `수용`(측정·설계 근거로 의식적 허용) · `연기`(해당 마일스톤에서 처리) · `미결`(과소평가·명시 결정 필요) · `완화`(대응됨).
- **심각도**는 "발현 시 영향" 기준이며 발현 확률과 별개다.

트리거: 파이프라인 구조 평가(2026-07-09). 근거는 [M4b](measurements/M4b.md)·[M-http-capacity](measurements/M-http-capacity.md)·[ADR 0007](decisions/0007-messaging-storage-redis-streams-and-governance.md).

## 요약

| ID | 리스크 | 심각도 | 상태 |
|---|---|---|---|
| **R1** | Redis 장애 시 스트림 버퍼·offset 유실("내구"가 앱 크래시까지만) | 높음 | **미결** |
| **R2** | 지속 과부하 시 조용한 트림 유실 + 서버측 admission 없음("202=저장 보장"이 조건부) | 중간~높음 | **미결** |
| **R3** | 인입·소비자 CPU 경합 + 단일 박스 다축 포화, 수평 확장 미실증 | 중간 | 연기(M8) |
| **R4** | 컨슈머 용량이 수동이고 부족하면 조용히 유실 | 중간 | 미결(패턴) |
| R5a | device UPSERT가 적재 핫패스에 결합 | 낮음 | 수용 |
| R5b | monitoring PEL(pending) 상한 없음 | 낮음 | 관찰 |
| R5c | JSON 파싱·검증이 인입 CPU 지배분 | 낮음 | 수용 |

---

## R1 — Redis 버퍼 내구성 (미결, 심각도 높음)

**리스크.** Redis가 영속화 끔(`--save "" --appendonly no`) + 단일 인스턴스다. Redis가 죽으면 스트림 버퍼(최대 `MAXLEN 400K` ≈ 12K/s에서 ~33초치, 14K에서 ~28초치)와 **모든 컨슈머 그룹 offset이 통째로 유실**된다. 내구 경로(`storage`)조차 방어가 없다.

**왜 과소평가됐나.** M4b가 실증한 "재시작 무손실·무중복"은 **앱 크래시**에 대한 것이다(storage가 자기 pending을 재처리). **Redis 크래시**는 그 오라클 밖이라, "내구 파이프라인"이라는 인상이 실제 방어 범위를 넘어선다.

**처리 방향.** 허용 여부를 **명시 결정**으로 남긴다 — (a) "텔레메트리는 그 정도 순간 유실 허용"이면 근거·허용 윈도우를 SLO에 적고, (b) 아니면 Redis AOF(everysec) 또는 복제(Sentinel/Cluster) 도입. AOF는 디스크·지연 비용이 있으니 측정 게이트. 지금은 방향만.

## R2 — 조용한 트림 유실 + admission 부재 (미결, 심각도 중간~높음)

**리스크.** 백프레셔 정책이 "oldest 트림"(blind MAXLEN)이고 **트림은 무카운터**다. XADD는 자가 트림으로 항상 성공 → 클라이언트는 **항상 202**를 받는다. 그런데 `storage`가 자기 용량(정상상태 ≈12K, [M4b §후속](measurements/M4b.md))을 넘겨 400K 이상 밀리면 그만큼 **조용히 버려진다**. 즉 **"202 = 저장 보장"이 지속 과부하에선 거짓**이 된다(정상상태 ≤용량에선 lag 0이라 참).

**공백.** 서버가 과부하일 때 **429/503로 디바이스에 백오프 신호를 주는 admission이 없다**. M4b가 "우아한 백프레셔"라 부른 것은 부하 생성기(k6) 측 드롭이지 서버측 거절이 아니다.

**처리 방향.** SLO 문서에 **"202=저장 보장은 인입 ≤ storage 용량 조건"** 을 명시. 필요 시 스트림 lag/depth 기반 429 이음새를 `TelemetryIngestService` 앞단에 둔다(내구성 트레이드오프: XTRIM MINID 대안은 메모리 무한 리스크, ADR 0007 참조).

## R3 — CPU 경합 + 단일 박스 포화 (연기 → M8)

**리스크.** 인입(파싱·검증 CPU)과 `storage` 워커가 **같은 코어**를 공유한다 → 워커를 늘리면 인입 CPU를 뺏는다(12K에서 워커 8→12가 지속 처리량을 못 올린 원인의 일부). 그리고 12K에서 **CPU ~90% + 디스크 ~94% 동시 근접** = 여유가 거의 없다. 수평 확장 경로(앱 다중 인스턴스·Redis 클러스터·DB 분리)가 아직 하나도 실증되지 않았다.

**상태.** ROADMAP **M8(배포 분리)** 로 연기됨(의식적). 지금은 "한 박스를 꽉 채우면 ~12K"까지만 특성화됨.

**처리 방향.** M8에서 앱/DB/Redis 분리 후 재측정. 그때 인입·소비자 CPU 분리가 실제 처리량을 얼마나 여는지 확인.

## R4 — 컨슈머 용량 수동 + 부족 시 조용한 유실 (미결, 패턴)

**리스크.** 컨슈머 그룹별 병렬화가 **각각 수동 노브**다(`storage`=12·`monitoring`=1·`geofence`=1). 처리율이 부족한 그룹은 **말없이 뒤처져 유실**한다 — `geofence`가 그 사례(lag = MAXLEN 400K, 판정 누락). 새 컨슈머를 붙일 때마다 **용량 계획을 수동으로** 해야 하고, 부족을 자동으로 알리는 장치가 없다.

**처리 방향.** geofence 자체는 다중 컨슈머(shared subscription)나 배치 판정으로 스케일(별도 작업). 구조 차원에선: **내구 컨슈머는 사이징 + lag 알림**(임계 초과 시 경보), **best-effort 컨슈머는 유실 허용을 명시**. 자동 스케일은 별도 결정.

## R5 — 잔가지

- **R5a device UPSERT 핫패스 결합 (수용).** 매 배치가 device 갱신(죽은 튜플→autovacuum)을 텔레메트리 쓰기 경로에 얹는다. `fillfactor=70`·HOT로 튜닝됨. **on-path perf 비용은 사실상 무시 가능**으로 귀결(2026-07-09): 배치 운영점이 CPU 바운드([M-http-capacity](measurements/M-http-capacity.md) — device upsert **켠 채** 12–16K 도달·디스크 68% 여유)라 UPSERT를 빼도 처리량은 안 오른다(별도 A/B 불필요). **남은 개선 유인은 성능이 아니라 구조**: registry↔live-state 분리 + M4 스펙 "status=파생" 이행 + status ONLINE-only 버그. insert-if-absent 강등(`DO NOTHING`)을 준비(코드·테스트 green·미커밋)했으나 `perf:` 아닌 `refactor:`/M4c로 재프레임([STATUS](STATUS.md) 현재 포커스).
- **R5b monitoring PEL 상한 없음 (관찰).** best-effort라 ACK를 안 하면 pending(PEL)이 누적(메모리). 현재 ~200으로 작음. 지속 증가하면 상한/주기적 XACK 필요.
- **R5c JSON 파싱 인입 CPU (수용).** Jackson 역직렬화 + 검증이 인입 CPU의 지배분(≈0.3ms/req, [M-http-capacity](measurements/M-http-capacity.md)). 바이너리 프로토콜은 디바이스 계약 변경이라 별개 결정.

## 갱신 규칙

리스크가 완화되면 상태를 `완화`로 바꾸고 근거(ADR/측정) 링크를 단다. 새 리스크는 발견 시 추가(트리거·근거 명시). 결정으로 확정된 항목은 ADR로 승격하고 여기선 `수용`/`완화`로 남긴다.
