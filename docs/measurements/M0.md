# M0 — 기준선 (baseline)

> M0의 목표는 "개선"이 아니라 **정확한 기준점 확보**다. 이후 모든 마일스톤이 이 수치와 비교된다.

## 한눈에 (TL;DR)
- **처리량 천장 ≈ 33 req/s** — 열린·닫힌 모델 + iostat 산수가 모두 같은 자리.
- **병목 = HDD fsync** — CPU 유휴 · HikariCP 적체 · 디스크 %util 97% 3중 증거 + 산수로 확증.
- **다음(M1)** — 배치 적재로 요청당 fsync를 줄여 이 천장을 깬다.

## 핵심 결과

### ① 처리량 천장 ≈ 33 req/s

**닫힌 모델 baseline** (`telemetry-baseline.js`, 50 VU 2분, 3회 중앙값, 2026-06-29)
| 런 | 처리량 (req/s) | p95 (s) |
|---|---|---|
| 1 | 36.3 | 1.70 |
| 2 | 36.5 | 1.63 |
| 3 | 38.0 | 1.60 |
| **중앙값** | **36.5** | **1.63** |
> 에러율 0%·검증 거부율 0%(전부 202).

**열린 모델 capacity** (`telemetry-capacity.js`): **knee ≈ 33 1Hz 디바이스.** 도착률을 올려도 달성 처리량이 ~33에서 안 올라감(상세는 ↓측정 신뢰성).

> **닫힌 36.5 > 열린 33** — 닫힌 50VU는 50개가 동시에 커밋해 **group commit**이 fsync를 일부 묶어 처리량이 약간↑. 둘 다 fsync 바운드(33~38 밴드). 이게 M1 group-commit 레버의 예고편.

### ② 병목 = HDD fsync

**박스 `iostat -xzt 1 sda`** (런 D, 194 정착샘플 평균)
| 지표 | 값 | 의미 |
|---|---|---|
| `%util` | **96.8%** (max 118*) | 디스크 포화 (*>100은 보고 한계) |
| `f/s` (fsync/초) | **39.0** (max 52) | fsync 처리 속도 ≈ 천장 |
| `f_await` (fsync 대기) | **25.3 ms** | HDD 회전지연 — 근본 비용 |
| `w/s` / `w_await` | 87.6 / 17.6 ms | 쓰기 |
| `aqu-sz` | 2.62 | I/O 큐 적체 |

**맥 Grafana** (서버측, 모든 런 공통)
| 지표 | 값 | 의미 |
|---|---|---|
| `process_cpu_usage` | 최대 **0.02 ~ 0.08** | CPU 거의 유휴 → **CPU 바운드 아님** |
| HikariCP `pending`/`active` | 포화 ~190/~10 · 정착 ~0~20/~10 | 풀(기본10) 한계, 잉여 요청은 DB 쓰기 대기 |

**천장을 닫는 산수**
```
f_await ≈ 25ms        →  직렬 천장 ≈ 1000/25 ≈ 40 fsync/s
실측 f/s ≈ 39          (디스크가 fsync로 포화, %util 97)
달성 처리량 ≈ 33 req/s  →  요청당 fsync ≈ 39/33 ≈ 1.2
→ knee ≈ 40 ÷ 1.2 ≈ 33   ← 모든 런의 달성 처리량과 일치
```
요청당 ~1.2 = InnoDB redo flush + 트랜잭션 내 Device upsert UPDATE 등. **추측 아니라 산수로 닫힘.**

## 측정 환경
- 하드웨어: Intel i7-6700HQ 4c/8t · RAM 8GB · **5400rpm HDD**(쓰기 병목 — 절대수치는 디스크 종속, 비율로 해석).
- **자원 격리**: Locus = 박스 ≈3/4 (CPU core 0–5, 메모리 ~6G). 시스템 MySQL(idle)+OS에 1/4(코어 6–7, ~2G) 예약. 측정 내내 시스템 DB idle·고정, `free -h` Swap=0.
- OS: Ubuntu 22.04 / JVM: Temurin 21.0.11 / 힙 -Xms1500m -Xmx1500m, G1, taskset -c 0-5.
- DB: Locus MySQL 8.0.40 (docker, 3307, innodb_buffer_pool_size=2G, cpuset 0-5, mem_limit 3G) — 시스템 MySQL(3306)과 공존.
- 부하: 맥북 k6 → 박스, 유선 LAN, **RTT avg 0.81ms** (min 0.56 / max 0.95, ping ×10).
- 데이터 행수(baseline 측정 시작 시): **34,987** (앞선 capacity 런들로 누적 — 빈 DB 아님).
- 2-머신 전체 절차: **[RUNBOOK.md](RUNBOOK.md)**. Grafana p95 PromQL: `histogram_quantile(0.95, sum(rate(http_server_requests_seconds_bucket{uri="/api/telemetry"}[1m])) by (le))`.

## 측정 신뢰성 (과정 — "왜 33을 믿나")
> 결론이 아니라 결론의 근거. capacity는 4회 런으로, 측정 오염을 걷어내고 천장을 핀 과정이다.

| 런 | RATES | 달성 처리량 | p95 | dropped | 비고 |
|---|---|---|---|---|---|
| A | 20…70 | plateau ~33 | 30.8s | 1138 | knee 한참 초과 |
| B | 28…38 | 30/s | 8.36s | 205 | A 직후(미정착) |
| C | 28…38 | 31.4/s | **0.96s** | 0 | 정착(평균이 천장 아래) |
| D | 33…39 | 33.18/s | 6.74s | 119 | 천장 위 주행 + iostat 캡처 |

- **달성 처리량은 모든 런에서 ~33으로 견고** — 이게 진짜 불변값(닫힌 baseline 32.9 1회차 포함).
- **p95는 천장이 아니라 백로그 산물**: 도착률을 천장(~33) 위로 얼마나 미느냐 + 정착 상태에 따라 0.96s~30s로 출렁. 런 C가 깨끗했던 건 평균 도착률(31)이 천장 아래였기 때문이지 knee가 높아서가 아님.
- **측정 위생 교훈**: 초기 런(A·B)은 미정착·이전 백로그 잔류로 p95가 부풀려졌다 → "3회·정착·램프 버림"이 왜 필요한지의 실증.
- (정정 기록: 한때 잠정 ~36으로 봤으나, 런 C의 낮은 평균을 과독해한 것. 4런+iostat로 ~33 확정.)

## 해석 & 다음 (M1)
- **병목 = HDD fsync, 3중 확증**: CPU 유휴 + HikariCP 적체 + 디스크 %util 97%·f_await 25ms·f/s 39. 셋이 같은 결론.
- **풀 튜닝은 무의미**: 포화 런 pending 190인데 active 10에서 안 늚 → 커넥션을 늘려도 같은 fsync 앞에 줄 설 뿐. CPU 유휴라 풀은 비병목. (M1에서 풀 사이즈 스윕으로 실증 예정.)
- **M1에서 깨뜨릴 것**: 요청당 fsync(~1.2)를 **배치로 N건당 1회**로 줄인다. smoking gun = `f/s`(또는 `Innodb_data_fsyncs`)/req. Device upsert는 교란변수라 분리 측정(M1 A2-x). → [M1.md](M1.md).
