# M0 — 기준선 (baseline)

> 이후 모든 마일스톤이 이 수치와 비교된다. M0에서는 "개선"보다 **정확한 기준점 확보**가 목표.

## 측정 환경 실행 (재현 절차)
```bash
# 1) 인프라 + 측정 스택 기동 (mysql + prometheus + grafana)
docker compose --profile monitoring up -d

# 2) 앱을 호스트 JVM에서 실행 (GC·힙 측정을 깨끗하게)
./gradlew bootRun

# 3) 부하 — 둘 중 택1
k6 run load/telemetry-baseline.js                 # 주: k6 (단계적 VU 상승)
# ./gradlew bootRun --args='--spring.profiles.active=simulator'  # 보조: 현실적 움직임

# 4) 관측
#   Prometheus  http://localhost:9090
#   Grafana     http://localhost:3000  (PromQL: histogram_quantile(0.95, sum(rate(http_server_requests_seconds_bucket{uri="/api/telemetry"}[1m])) by (le)))
#   앱 메트릭    http://localhost:8080/actuator/prometheus
```
> 측정은 개인 온프렘 서버에서 수행하고, 완료된 마일스톤 커밋에 태그를 달아 블로그에서 그 태그를 링크한다(docs/conventions.md).

## M0 구현 선택 (단순 우선)
> 조기 최적화를 하지 않는다. 단순한 정답으로 두고, 측정으로 필요성이 확인되는 마일스톤에서 개선한다.
- 단건 insert (벌크는 적재 처리량이 한계에 닿으면 — M2)
- offset 페이징 (커서는 대용량 깊은 페이지에서 — M7)
- 새로고침 조회 (실시간 푸시는 라이브 모니터링 요구로 — M4)
