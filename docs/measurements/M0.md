# M0 — 기준선 (baseline)

> 상태: **측정 완료(2026-06-29)**. 후속 과제: [M1.md](M1.md) fsync 분할.
> 증거: Grafana 캡처(`img/m0-*.png`) + 원본 [M0-raw/](M0-raw/)(iostat·k6 출력).

## 목표
가장 단순한 구현(단건 insert, 커밋당 fsync)의 **최대 처리량과 병목**을 측정한다. 이 값이 이후 모든 마일스톤의 비교 기준이 된다.

## 문제 상황
단순 구현(요청 1건 = `@Transactional` 1개 = 커밋 1번)의 최대 처리량과 병목이 아직 측정되지 않았다.

## 해결 과정 (요약)
1. **최대 처리량 ≈ 33 req/s** — 열린 모델(capacity 포화점)과 닫힌 모델(50VU baseline)이 일치.
2. **병목 = HDD fsync** — CPU 유휴, 풀 적체, 디스크 포화가 동시에 나타난다.
3. **계산과 일치** — f_await 25ms → fsync 한계 40/s → 요청당 1.2 → 40÷1.2 ≈ 33.

## 해결 과정 (상세)

### 1. 최대 처리량 ≈ 33 req/s
최대 처리량은 ≈ 33 req/s다. 닫힌 모델(50VU 2분, 3회 중앙값)과 열린 모델(도착률 램프)이 일치한다:

| 모델 | 처리량 | 비고 |
|---|---|---|
| 닫힌 baseline (중앙값) | 36.5 req/s | p95 1.63s, 에러 0% |
| 열린 capacity (포화점) | ~33 req/s | 도착률을 올려도 더 오르지 않음 |

닫힌(36.5)이 열린(33)보다 약간 높은 것은 50VU 동시 커밋으로 **그룹 커밋(group commit)**이 fsync를 일부 묶기 때문이다.

```bash
k6 run -e BASE_URL=http://<박스IP>:8093 load/telemetry-baseline.js   # 닫힌 50VU 2분, 3회 중앙값
k6 run -e BASE_URL=http://<박스IP>:8093 load/telemetry-capacity.js   # 열린 도착률 램프
```

### 2. 병목 = HDD fsync
병목은 HDD fsync다. 세 신호가 동시에 이를 가리킨다: CPU 유휴, 풀 적체, 디스크 포화.

| 출처 | 지표 | 값 | 의미 |
|---|---|---|---|
| 박스 iostat | %util | 96.8% | 디스크 포화 |
| | f/s (fsync/초) | 39.0 | fsync 처리 한계 근처 |
| | f_await | 25.3ms | HDD 회전지연 |
| 맥 Grafana | process CPU | 0.02~0.08 | CPU 병목 아님 |
| | HikariCP pending/active | ~190 / ~10 | 풀 적체, 잉여 요청은 쓰기 대기 |

CPU가 유휴인데 디스크 fsync가 전체를 제한한다. 풀·JVM 튜닝은 효과 없고 fsync 횟수를 줄여야 한다.

<details><summary>측정 명령어</summary>

```bash
# 박스: 포화 런 중 디스크 캡처
iostat -xzt 1 sda > ~/iostat-runD.log
# Grafana: process_cpu_usage · HikariCP pending/active 패널 관측
```
</details>

### 3. 계산과 일치
계산도 33을 준다. 최대 처리량이 fsync 한계로 설명된다:

```
f_await ≈ 25ms        → fsync 직렬, 한계 ≈ 1000/25 ≈ 40 fsync/s
실측 f/s ≈ 39          (%util 97, 디스크가 fsync로 포화)
달성 처리량 ≈ 33        → 요청당 fsync ≈ 39/33 ≈ 1.2
→ 최대 처리량 ≈ 40 ÷ 1.2 ≈ 33
```
요청당 ~1.2 = InnoDB redo flush + 트랜잭션 내 device upsert UPDATE 등.

## 성과와 다음 단계
**성과**
- 최대 처리량 ≈ 33 req/s 확정. 열린·닫힌·계산 3중 일치.
- 병목 = HDD fsync. CPU 유휴 + 풀 적체 + 디스크 포화 + 계산이 같은 결론.

**다음 단계 (M1)**
- 풀·JVM 튜닝은 무효다(CPU 유휴, active가 안 늘어남). 줄일 것은 요청당 fsync다.
- 배치 적재로 N건당 fsync 1회로 낮춰 최대 처리량을 올린다. 핵심 지표 = 요청당 fsync(`Innodb_data_fsyncs`/req). → [M1.md](M1.md).

## 폐기한 시도와 교정한 가설
- **p95를 최대 처리량 지표로 잘못 봤다**: p95는 도착률·정착 상태에 따라 0.96s~30s로 변동한다(백로그 함수). 한계값은 처리량 plateau다. 런 C(p95 0.96s)가 낮았던 것은 평균 도착률(31)이 한계 아래였기 때문이지 포화점이 높아서가 아니다.
- **~36으로 잘못 읽음 → ~33 정정**: 런 C의 낮은 평균을 잘못 읽은 것. 4런 + iostat로 ~33 확정.
- **풀 튜닝은 무효**: 포화 런에서 pending 190인데 active는 10에서 안 늘어난다. 커넥션을 늘려도 같은 fsync에서 대기할 뿐이다.
