# M0 — 기준선 (baseline)

> 이후 모든 마일스톤이 이 수치와 비교된다. M0에서는 "개선"보다 **정확한 기준점 확보**가 목표.

## 측정 절차
2-머신 측정(SUT 박스 + 맥북 관측/부하)의 전체 절차는 **[RUNBOOK.md](RUNBOOK.md)** 참조.
Grafana p95 PromQL 예: `histogram_quantile(0.95, sum(rate(http_server_requests_seconds_bucket{uri="/api/telemetry"}[1m])) by (le))`.
> 측정은 타깃 박스에서 수행하고, 완료된 마일스톤 커밋에 태그를 달아 블로그에서 그 태그를 링크한다(docs/conventions.md).

## 환경 (측정 시 채움)
- 하드웨어: Intel i7-6700HQ 4c/8t · RAM 8GB · **5400rpm HDD**(쓰기 병목 — 절대수치는 디스크 종속, 비율로 해석)
- **자원 격리**: Locus = 박스 ≈3/4 (CPU core 0–5, 메모리 ~6G). 시스템 MySQL(idle)+OS에 1/4(코어 6–7, ~2G) 예약. 측정 내내 시스템 DB idle·고정, `free -h` Swap=0.
- OS: Ubuntu 22.04 / JVM: Temurin 21.0.11 / 힙: -Xms1500m -Xmx1500m, G1, taskset -c 0-5
- DB: Locus MySQL 8.0.40 (docker, 3307, innodb_buffer_pool_size=2G, cpuset 0-5, mem_limit 3G) — 시스템 MySQL(3306)과 공존
- 부하: 맥북 k6 → 박스, 유선 LAN (RTT 기입) / 시나리오: baseline 또는 stress
- 데이터 행수(측정 시작 시): (작성)

## M0 구현 선택 (단순 우선)
> 조기 최적화를 하지 않는다. 단순한 정답으로 두고, 측정으로 필요성이 확인되는 마일스톤에서 개선한다.
- 단건 insert (벌크는 적재 처리량이 한계에 닿으면 — M2)
- offset 페이징 (커서는 대용량 깊은 페이지에서 — M7)
- 새로고침 조회 (실시간 푸시는 라이브 모니터링 요구로 — M4)
