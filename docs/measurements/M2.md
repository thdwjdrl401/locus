# M2 — 적재 저장소 MySQL → TimescaleDB (랜덤 → 순차 쓰기)

> 상태: **측정 완료(2026-06-30)**. 트리거: [M1.md](M1.md). 결정: [ADR 0008](../decisions/0008-telemetry-store-timescaledb.md). 후속 과제: [M2-par.md](M2-par.md) 워커 병렬화.

## 목표
저장 구조를 순차 쓰기로 바꿔 포화점을 올린다. 대상은 M1의 잔여 병목(data fsync = InnoDB B-tree의 랜덤 쓰기)이다.

## 문제 상황
포화점 1,437은 InnoDB B-tree의 랜덤 쓰기 fsync가 묶는다. M1 배치로 커밋 fsync는 풀었으나(%util 94%, data fsync/req 0.059) 남은 병목은 제자리 갱신의 랜덤 fsync(doublewrite·페이지 플러시)다. 커밋 횟수와 무관이라 배치·flush로는 못 줄인다.

## 해결 과정 (요약)
1. **저장소 교체(한 변수)** — MySQL(InnoDB B-tree) → TimescaleDB 하이퍼테이블(시간 청크 append). 나머지 고정.
2. **포화점 1,437 → 5,459 (약 3.8배)** — 디스크 %util 94% → 59%, 평균 쓰기 크기 → ~200KB(순차).
3. **병목 이동 → 단일 배치 워커** — 디스크가 여유인데 포화가 생긴다.

## 해결 과정 (상세)

### 1. 순차화로 포화점 3.8배
포화점이 1,437 → 5,459로 3.8배 올랐다. 바꾼 변수는 저장 엔진 하나다(나머지 M1 A2와 동일):

| 구분 | Before (M1 A2c, MySQL) | After (TimescaleDB) | 배수 |
|---|---|---|---|
| 포화점 | 1,437 req/s | **5,459 rows/s** | **~3.8배** |
| 디스크 %util | 94% (포화) | **59%** (여유) | |
| 평균 쓰기 크기 | 작음(랜덤 페이지) | **~200KB**(순차) | |
| 병목 | 디스크(랜덤 fsync) | **단일 배치 워커** | |
| 내구성 | flush=1 | synchronous_commit=on | 동등 |
| p95 / 에러 | — | 654µs / 0% | |

<details><summary>측정 명령어</summary>

```bash
# 박스: 매 런 전 truncate (변수통제)
psql> TRUNCATE telemetry, device;
# 앱: INGEST_MODE=queue (배치 워커 1, batch-size=500, max-delay-ms=200) — M1 A2와 동일
# 맥: 도착률 램프
mac$ k6 run -e BASE_URL=http://<박스IP>:8093 -e RATES=100,1000,3000,5000,6000 load/telemetry-capacity.js
```
포화 신호 = `locus_ingest_inserted_total` plateau + `locus_ingest_dropped` 상승 + 큐 만석(p95 아님 — 즉시 202).
</details>

### 2. 디스크는 더는 병목이 아니다
디스크는 더는 병목이 아니다. 피크 처리량(5,459)에서 %util이 59%로 내려간다. 처리량이 높을수록 배치가 더 큰 순차 쓰기로 뭉쳐(평균 쓰기 25KB → 200KB) 디스크를 효율적으로 쓴다. HDD 대역폭 기준으로는 ~2%만 사용한다. MySQL이 94%·1,437에서 랜덤 fsync로 막혔던 것과 대비된다 — 순차화가 병목을 풀었다.

### 3. 병목 이동 = 단일 배치 워커
이제 병목은 단일 배치 워커다. 디스크가 여유인데 포화가 생기는 지점이 단일 스레드 워커 + 커넥션 1개(직렬 처리율)다. 포화는 큐 깊이가 ~9,000/10,000까지 차고 드롭이 오르며 발생한다(부하 차단, 붕괴 아님). HikariCP active=1. 다음 개선점은 워커 병렬화다. → [M2-par.md](M2-par.md).

## 성과와 다음 단계
**성과**
- 포화점 1,437 → 5,459 (약 3.8배), 내구성 동등(synchronous_commit=on ≈ flush=1). 디스크 병목 해소.
- 순차화 증거 확보. %util 94% → 59%, 평균 쓰기 25KB → 200KB.

**다음 단계 (M2-par)**
- 병목이 단일 배치 워커로 이동했다. 디스크 여유(59%)를 워커 병렬화로 채워 10k SLO 방향으로 올린다.

## 측정 환경·지표
| 항목 | 값 |
|---|---|
| 박스(SUT) | i7-6700HQ 4c/8t · 8GB · 5400rpm HDD |
| 격리 | `taskset -c 0-5` · `-Xmx1500m` |
| DB | TimescaleDB 2.17.2-pg16 (docker). `synchronous_commit=on`·`fsync=on`(durable, MySQL flush=1과 동등), `shared_buffers=2GB`(MySQL buffer_pool과 동일), cpuset 0-5, mem 3g |
| 스키마 | Flyway V1 — telemetry 하이퍼테이블(복합 PK `device_id`+`recorded_at`), `INSERT … ON CONFLICT DO NOTHING`, `reWriteBatchedInserts` |
| 앱 | `INGEST_MODE=queue`(배치 워커 1), batch-size 500, max-delay 200ms, 포트 8093 |
| 부하 | 맥 → 박스, k6 `telemetry-capacity.js`(열린 도착률 램프), 매 런 truncate |

| 지표 | 정의 | 판정 |
|---|---|---|
| 포화점 | `inserted_total` plateau (rows/s) | queue 모드 = `dropped` 상승·큐 만석 |
| 순차화 | 디스크 %util · 평균 쓰기 크기 | 성공 = %util↓ + 쓰기 크기↑ |
| 병목 이동 | %util 내려가는데 처리량 정체 | 디스크 아닌 곳(워커·CPU·풀) |

> 공정성: 같은 워크로드·같은 내구성에서 저장 구조(랜덤→순차) 효과로 해석한다. 엔진 1:1 마이크로벤치가 아니다. 절대수치는 이 HDD 종속 → 비율로 해석.

## 폐기한 시도와 교정한 가설
- **처음 세 런의 실패는 서버가 아니라 k6 스크립트 결함이었다**: ~2,200–2,333 rows/s에서 HTTP 81–85% 실패가 나 인테이크/Tomcat 병목으로 잘못 판단했다. Prometheus를 status별로 조회하니 실패가 전부 400(CLIENT_ERROR) — `@ValidTimestamp`(미래 60s)가 거절한 것이었다. k6가 `recorded_at = base + i`(1ms/iter)로 생성해 >1,000 req/s에서 미래로 표류해 윈도우를 넘겼다. 서버는 정상이다(미래 거절이 옳다). 스크립트를 실제 시각(`new Date()`)으로 고친 뒤 5,459가 나왔다. 부하 생성기도 측정 대상이다. (오판했던 Tomcat 커넥터 상향은 무해해 유지.)
