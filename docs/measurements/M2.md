# M2 — 적재 저장소 MySQL → TimescaleDB (랜덤→순차 쓰기)

> 상태: **측정 완료(2026-06-30)**. 결과: 포화점 1,437 → **5,459 rows/s(~3.8×)**, 디스크 병목 해소, 병목이 단일 배치 워커로 이동.
> 결정: [ADR 0008](../decisions/0008-telemetry-store-timescaledb.md). 트리거 측정: [M1.md](M1.md).

## 0. 질문 한 줄
**M1 잔여 병목(data fsync = InnoDB B-tree 랜덤 쓰기)을 순차 쓰기(TimescaleDB 하이퍼테이블)로 바꾸면 포화점이 오르는가, 그리고 병목이 어디로 이동하는가.**

## 1. 가설 (M1에서 이어짐)
- M1 A2: 배치로 redo fsync는 풀었으나 포화점 1,437에서 여전히 디스크가 병목(%util 94, data fsync/req 0.059). 남은 병목 = B-tree 제자리 갱신의 랜덤 fsync.
- TimescaleDB 하이퍼테이블은 시간 청크에 append → 랜덤 쓰기를 순차화. **같은 HDD로도 포화점이 오를 것**으로 기대.
- 반증 가능: 순차화해도 포화점이 안 오르면 → 병목이 디스크 랜덤성이 아니라 다른 곳(WAL fsync·CPU)이었다는 뜻.

## 2. 결정적 증거 지표 (node_exporter→Grafana)
- **포화점**(rows/s) — queue 모드라 `locus_ingest_inserted_total` rate가 plateau + `locus_ingest_dropped` 상승 + 큐 깊이가 capacity(10,000)로 참(p95 아님 — 202 즉시 반환).
- **디스크**: `node_disk_*` → %util · 평균 쓰기 크기 · 쓰기 지연. 순차화 성공이면 같은/더 높은 처리량에서 %util 여유 + 평균 쓰기 크기↑.
- **병목 이동**: 디스크 %util이 내려가는데 처리량이 더 안 오르면 → 디스크가 아니라 다른 곳(워커·CPU·풀)이 병목.

## 환경
- **박스(SUT)**: i7-6700HQ 4c/8t, 8GB, 5400rpm HDD. JDK21. `taskset -c 0-5` + `-Xmx1500m`.
- **DB**: TimescaleDB `2.17.2-pg16`(docker), `shared_buffers=2GB`(M0/M1 MySQL buffer-pool 2G와 동일), `synchronous_commit=on`·`fsync=on`(durable, MySQL flush=1과 동등). cpuset `0-5`, mem 3g. 스키마=Flyway V1(telemetry 하이퍼테이블, 복합 PK device_id+recorded_at).
- **앱**: `INGEST_MODE=queue`(배치 워커 1개), `batch-size=500`, `max-delay-ms=200`. 포트 8093.
- **부하**: 맥 → 박스. k6 `load/telemetry-capacity.js`(열린 모델, 도착률 램프). 2-머신([RUNBOOK](RUNBOOK.md)).
- **측정 위생**: 매 런 전 `TRUNCATE telemetry, device;`.

| 지표 | 값 |
|---|---|
| 포화점 | **1,437 req/s** |
| data fsync/req | 0.059 |
| 디스크 %util | 94% (포화) |

## 변경 내용
- 저장소 MySQL(InnoDB B-tree) → TimescaleDB(PostgreSQL 하이퍼테이블). 앱 전체 PostgreSQL 단일 교체, MySQL 제거.
- telemetry: 복합 PK `(device_id, recorded_at)` + `create_hypertable`(recorded_at 시간 파티셔닝). 적재 = `INSERT ... ON CONFLICT DO NOTHING`(멱등), `reWriteBatchedInserts`로 멀티로우 배치.
- 배치 크기·워커·k6 시나리오는 M1 A2와 동일 — **바뀐 변수는 저장 엔진 하나.**

## After (TimescaleDB, durable, 2026-06-30)
도착률 램프 100→6,000 rows/s, 정상상태 관측:

| 구분 | Before (MySQL) | After (TimescaleDB) | 배수 |
|---|---|---|---|
| 포화점 | 1,437 req/s | **5,459 rows/s** | **~3.8×** |
| 포화 시 디스크 %util | 94% (포화) | **59%** (여유) | |
| 평균 쓰기 크기 | 작음(랜덤 페이지) | **~200KB** (순차) | |
| 병목 위치 | 디스크(랜덤 fsync) | **단일 배치 워커**(디스크 여유) | |
| 내구성 | flush=1 | synchronous_commit=on | 동등 |
| p95 / 에러 | — | 654µs / 0% | |

- 디스크 %util은 **중간 부하(~3,500 rows/s)에서 88.7%로 정점, 피크 처리량(5,459)에선 오히려 59%로 하락**. 처리량↑일수록 배치가 더 큰 순차 쓰기로 뭉쳐(평균 쓰기 크기 25KB→200KB) 디스크를 *더 효율적으로* 씀.
- 포화는 **큐 깊이가 ~9,000/10,000까지 차고 드롭이 상승**하며 발생(우아한 부하 차단, 붕괴 아님). HikariCP active=1.

## 해석
1. **포화점 1,437 → 5,459 (~3.8×).** 디스크 병목이 풀렸다.
2. **디스크는 더는 병목이 아니다**: 피크에서 59%, 평균 쓰기 200KB(순차). MySQL은 94%·1,437에서 랜덤 fsync로 막혔는데, TimescaleDB는 59%로 3.8배 — **"랜덤이 병목이었나"의 답 = 그렇다, 순차화가 풀었다.** (HDD 대역폭은 ~2% 사용 — 한참 여유.)
3. **병목 이동**: 디스크 여유인데 포화가 생긴 곳 = **단일 스레드 배치 워커 + 커넥션 1개**(직렬 처리율). 다음 개선 지점 = **워커 병렬화**(디스크 여유 → 10k SLO 향, durable 유지 가능성). 별도 마일스톤.
4. **공정성**: synchronous_commit=on·fsync=on·shared_buffers=2GB로 MySQL flush=1과 동등 durable. 엔진 1:1 마이크로벤치가 아니라 "같은 워크로드·같은 내구성에서 저장 구조(랜덤→순차) 효과"로 해석한다.

## 측정 함정 (정직 기록)
처음 세 런이 ~2,200–2,333 rows/s에서 "하드-0 붕괴"(HTTP 81–85% 실패)로 보여, 인테이크/Tomcat 병목으로 오진했다. Prometheus를 status별로 조회하니 실패가 전부 **400(CLIENT_ERROR)** — `@ValidTimestamp`(미래 60s)가 거절. k6 스크립트가 `recorded_at = base + i`(1ms/iter)로 생성해 **>1,000 req/s에서 실제 경과시간보다 미래로 표류** → 윈도우 초과. **서버는 정상(미래 거절은 옳음).** 스크립트를 실제 시각(`new Date()`)으로 고친 뒤 5,459가 나왔다. → **부하 생성기도 측정 대상이다.** (오진했던 Tomcat 커넥터 상향은 무해해 유지.)
