# M-e2e-soak — 전 구간 통합 소크 + 지속 천장 규명

> 상태: **측정 완료(2026-07-12)**. 트리거: 그동안 저장 계층(M2-sustain 63분 10k)·스트림 fan-out([M4b](M4b.md))·MQTT 수집([M-MQTT](M-MQTT.md))을 **각각 따로** 특성화했을 뿐, HTTP→Redis Streams→TimescaleDB **전 구간을 한 번에 60분+** 돌린 적이 없었다. 이 소크가 "저장은 63분, 나머지는 각각 별도"라는 헤지를 지운다. 후속으로 지속 처리량 천장이 어디인지 규명한다.

## 목표
전 구간(HTTP 수집 → `XADD` → Redis Streams `storage`·`monitoring` 컨슈머 그룹 → TimescaleDB 적재)을 60분 이상 10k로 돌려 **무손실을 양끝에서 정산**하고, **지속 천장의 위치**를 규명한다.

## 측정 환경
| 항목 | 값 |
|---|---|
| SUT(박스) | i7-6700HQ 4c/8t · 8GB · 5400rpm HDD, 앱 코어 0–5 핀·힙 1.5G |
| DB | TimescaleDB 2.17.2-pg16, 5분 청크 + 12h retention, durable(`synchronous_commit=on`) |
| 인입 | `stream` 프로파일, storage 워커 4, MAXLEN 400K, device upsert on(main) |
| 부하 | 맥에서 k6 `telemetry-fleet.js`, 1 VU=1 디바이스 1Hz, `DEVICES=10000` |
| 관측 | 맥의 Prometheus(박스 앱 `/actuator/prometheus` + node_exporter 스크레이프) |

## 결과 1 — 전 구간 60분+ 무손실 (양끝 교차검증)

66분 런(램프 60s + 유지 65분), 유지 구간 19:35–20:36(≈61분).

| 지표 | 값 |
|---|---|
| accepted 202/s(지속) | 평균 9,812 · min 9,080 · max 9,996, 실패 0.00% |
| 서버 처리 p95 / p99 | 24ms / 32ms (avg 9ms) |
| 클라이언트 p95 (k6) | 209ms |
| flush 평균 | 197ms |
| 디스크 %util | 70%(65–77%) |
| HikariCP pending / active | 0 / ~4 |
| node CPU(전코어) | ~87% |

**무손실 정산 — 보낸 쪽·받은 쪽·저장한 쪽이 일치.** k6 발신 요청 **38,616,836** ≈ Redis 스트림 수신(`entries-read`, storage·monitoring 각각) **38,617,038**(차 202건, 0.0005%). 여기에 storage **pending 0 · lag 0 · poison 0 · flush errors 0**. storage 컨슈머는 적재 성공 후에만 `XACK`하므로 pending 0 = 읽은 전량이 DB 적재됨, lag 0 = 안 읽은 엔트리 없음, poison 0 = 읽기 전 트림된 엔트리 없음. 즉 `XADD`된 모든 텔레메트리가 TimescaleDB에 적재됐다. MAXLEN 400K로 트림된 건 전부 이미 소비·ACK된 엔트리다.

## 결과 2 — 지속 천장 = 부하기(맥), 파이프라인 아님

소크가 10k를 정확히 못 채우고 ~9.8k(accepted min 9,080)로 평균난 이유를 규명했다. 결론: **단일 맥 부하기가 천장이고 서버는 여유였다.**

규명 순서(시간순):
1. **진단 런(스레드풀 300, Tomcat 메트릭 on, 12분).** busy 워커 스레드가 **300(=maxThreads)에 붙음.** Little 법칙으로 설명된다: 10k/s를 서버 처리 30ms에 내려면 동시 처리수 = 9,983 × 0.030 ≈ **300**. 풀이 그 값과 맞아 붙은 것이지 포화 대기가 아니다. 서버 p95 30ms인데 클라 175ms — 갭은 커넥터 큐 대기.
2. **clean 런(별도 12분).** accepted **10,000/s 평평**, 서버 p95 21ms, disk 68% → **9.7k는 천장이 아니다.**
3. **라이브 하강 포착.** 처리량이 9,979→9,481로 떨어지는 내내 **서버 p95 22ms · GC 0 · disk 70% · XADD 5ms 전부 정상.** 닫힌 루프에서 서버가 빠른데 처리량이 떨어진다 = 요청이 안 도착한다 = 부하기가 못 보낸다.
4. **맥 직접 확인.** load average **11.47**(논리 코어 10 초과) · CPU sys **35%**(1만 소켓 syscall) · 여유 램 **76MB + compressor 11G**(메모리 고갈) · k6 프로세스 136%. 부하기 포화 확증. 맥이 k6 1만 VU + 모니터링 스택(Prometheus·Grafana도 이 맥)을 co-location으로 돌리다 임계를 넘겼다.

닫힌 루프 함의: 처리량 = 10,000 / max(1s, R_client). 서버 R이 작고 안정적이면(20–25ms) 사이클이 1s에 고정돼 10k 평평. 부하기가 밀려 R_client가 1s를 넘기면 그만큼 하강. 이번 하강은 서버가 아니라 맥에서 R이 벌어진 것이다. [M-http-capacity](M-http-capacity.md)의 "단일 부하머신 먼저 포화"를 재확인한다.

## 결과 3 — 가상 스레드는 회귀 (기각)

**가설(오판): 스레드풀 300이 1만 동시연결에서 300에 붙으니(결과 2-1), 가상 스레드로 상한을 없애면 처리량이 오른다.**

측정은 반대였다. 처리량 8,036/s(↓), 서버 p95 726ms(↑ 25배), 클라 p95 1.81s, behind_schedule 176만.

분석: XADD on-wire 3–8ms(정상) · app CPU 0.3 · disk 35% · HikariCP 0 — 자원이 전부 유휴인데 요청 wall-clock만 폭증했다. 요청이 700ms 중 대부분을 대기했는데 자원은 논다 = 처리 능력이 고정된 **공유 직렬화 지점**에 큐가 쌓였다. Lettuce는 기본이 연결 1개 멀티플렉싱이라, 무제한 admission(동시 ~1,600 in-flight)이 그 단일 연결의 명령 큐를 깊게 만들어 대기가 wall-clock에 나타난 것으로 본다. 바운드 풀(300)은 그 큐를 얕게 유지한 admission control이었다.

미확인: 직렬화 지점이 Lettuce 단일 연결인지 핫패스 `synchronized`의 캐리어 핀인지는 스레드 덤프/async-profiler가 필요하다. 단정하지 않는다.

결정: **바운드 스레드풀 유지, 가상 스레드 미채택.** Java 21이라 켤 수 있으나 이 워크로드에서 회귀.

## 오판 기록
- **"9.7k = 파이프라인 천장" 오인**을 여러 단계 거쳐 정정했다. 처음 disk 사용률(37% vs 70%)·DB 신선도에 귀속했으나, 후속 clean 런이 disk 68%에서도 10k 평평이라 그 상관을 반증. 최종 규명은 서버측 정상(22ms) + 맥측 포화(load 11.47·mem 고갈)로 부하기 확정.
- **가상 스레드가 개선일 것이라는 가설**을 측정으로 기각(위 결과 3).
- 런들이 DB 신선도·길이·박스 상태에서 통제되지 않았다 → 단일 런 값이며 3회 중앙값이 아니다. 무손실·부하기 천장 결론은 서버측 지표와 맥측 지표가 맞물려 견고하나, 런 간 지연 차이의 세부 귀속은 주장하지 않는다.

## 부수 확인
- `SERVER_TOMCAT_MBEANREGISTRY_ENABLED`는 관측 전용(MBean 등록)이라 성능 무관. 가상 런에도 켜져 있었고 결과는 최악이었으며, 동일 설정 두 런이 다른 결과를 냈다 → 이 플래그는 안정성의 원인이 아니다.
- `locus.ingest.flush`는 히스토그램 없는 Timer라 Prometheus에 count/sum(평균)만 있고 p95/p99가 없다. 지연 헤드라인은 k6 `http_req_duration`을 쓴다.

## 한계
- 닫힌 루프 1Hz 페이싱은 도착을 매끄럽게 만든다. 실제 함대의 상관된 버스트(재접속·리트라이·동기 wakeup)는 미측정이라 이 소크는 best-case에 가깝다.
- 지속 천장은 부하기라 파이프라인의 진짜 천장은 아직 미측정(서버 여유: p95 24ms·disk 70%).

## 성과
- 전 구간 60분+ 무손실을 **양끝 정산**(k6 발신 = 스트림 수신 = 전량 적재, lag·pending·poison 0)으로 확정. sub-path별 헤지 제거.
- 지속 천장이 **단일 맥 부하기**임을 규명. 서버측 헤드룸(p95 24ms·disk 70%) 확인.
- 가상 스레드 회귀를 측정으로 기각, 바운드 풀 유지.
- device upsert on(main)이 이 부하에서 병목 아님 재확인(HikariCP pending 0, 61분 평평) — device 데모션의 perf 명분 소멸을 뒷받침([RISKS.md](../RISKS.md) R5a).
