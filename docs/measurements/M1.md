# M1 — 적재 포화점 깨기: fsync 분할 실험 (설계서)

> **상태: 설계 완료 / 측정 대기**(집 LAN 박스 필요). 집 가면 아래 표만 채운다.
> M0에서 잡은 병목(`단건 insert + 커밋당 HDD fsync → ~33 req/s 포화점`)을 **MySQL 안에서 먼저 짜낸다.**
> 외부 브로커는 여기서 안 쓴다 — 이 실험이 "왜 그냥 배치로 안 끝나고 브로커가 필요한가(= fan-out/생존)"의 답을 측정으로 만들어 준다. 브로커 = Redis Streams(M4), Kafka 아님([ADR 0007](../decisions/0007-messaging-storage-redis-streams-and-governance.md)).

---

## 0. 질문 한 줄
**fsync를 줄이면 적재 포화점이 어디까지 올라가나, 그리고 그게 디스크가 병목이라는 증거를 어떻게 확증하나.**

## 1. 가설 (M0에서 이어짐)
- 현재 경로: 요청 1건 = `@Transactional` 1개 = **커밋 1번 = fsync ≥1번**. 포화점 ~33 req/s.
- 5400rpm HDD 랜덤 IOPS ~75 → 커밋당 fsync 여러 번(redo + doublewrite 등) + Device upsert UPDATE가 겹쳐 ~33로 떨어진 것으로 **추정**. 실측으로 확인한다.
- **fsync 횟수를 줄이는 두 축**:
  - (a) **여러 줄을 한 트랜잭션에** 묶는다(배치/벌크 insert) → fsync 1번이 N줄 커버.
  - (b) **커밋당 fsync 자체를 줄인다**(`innodb_flush_log_at_trx_commit` 완화) → 내구성↔처리량 트레이드오프.

## 2. 결정적 증거 지표
숫자 없으면 개선이 아니다. 포화점(req/s)만 보지 말고 **fsync/req**를 직접 잰다:
- `SHOW GLOBAL STATUS LIKE 'Innodb_data_fsyncs'` 의 **델타 / 처리한 요청 수** = **요청당 fsync 횟수**.
- 이게 줄어드는 만큼 포화점이 오르면 → "병목은 fsync였다"가 **증명**된다(상관이 아니라 인과).
- 보조: 박스 `iostat -x 1`의 디스크 `%util`(100%→탈출), `Innodb_os_log_fsyncs`, MySQL `Com_commit` 레이트.

## 3. 비교군 — 한 번에 한 변수만 (계획서 §3.1)
모두 같은 부하(`telemetry-capacity.js`, 1Hz 디바이스 ramping-arrival)로 포화점을 잰다.

| Arm | 변경 | 내구성 | 코드/설정 | 의도 |
|---|---|---|---|---|
| **A0** | 현재 단건 insert(@Transactional/req) | 안전(flush=1) | 변경 없음 | **Before**(= M0 포화점 재확인) |
| **A1** | `innodb_flush_log_at_trx_commit=2` | 약함(정전 시 ~1s 손실) | DB 설정만, 코드 0 | 커밋당 fsync 비용만 분리 측정 |
| **A2** | 앱 배치 적재(버퍼 N건 → 한 tx, JDBC batch) | 안전(flush=1) | 코드 변경 | "그냥 배치"만으로 어디까지 |
| **A3** | A2 + `flush=2` 결합 | 약함 | 코드+설정 | 두 축 합산 상한 |
| **A2-x** | A2에서 **Device upsert 분리/제거** | 안전 | 코드 변경 | 교란변수(핫패스 UPDATE) 영향 격리 |

> **교란변수 주의:** 현재 `ingest()`는 트랜잭션 안에서 Device upsert(`findByDeviceId` + `save`=UPDATE)를 **매 요청** 한다. Telemetry insert만의 효과를 보려면 A2-x로 분리한다(예: upsert를 비동기/주기 배치로, 또는 풀이 2000이라 디바이스별 1회만 INSERT되게).

### A2 구현 메모 (집 가서 코딩할 때)
- HTTP는 지금처럼 **202 즉시 응답**(컨트롤러 주석에 이미 "M2 비동기 큐 전환과 호환"). 수신 → 인메모리 큐(`BlockingQueue`) → 주기/크기 트리거 flush 워커가 **한 tx로 N건 saveAll**.
- **JDBC 배치가 실제 멀티로우로 나가려면** datasource URL에 `rewriteBatchedStatements=true` 필수(없으면 N번 왕복 — 네트워크 절감 0). Hibernate `hibernate.jdbc.batch_size=N`, `order_inserts=true`.
- flush 트리거 2변수: **배치 크기**(예 50/200/500)와 **최대 지연**(예 50ms/200ms). 크기↔지연↔처리량 곡선을 그린다.
- **유실 위험**: 인메모리 큐는 앱 크래시 시 버퍼 손실 → 이게 정확히 fan-out 브로커(Redis Streams, M4 — 별도 프로세스라 앱 크래시 생존 + `XPENDING`/`XCLAIM` 복구)가 사는 지점. A2의 한계로 **명시 기록**한다.

## 4. 측정 절차
2-머신(박스 SUT + 맥 부하/관측)은 [RUNBOOK.md](RUNBOOK.md).

**변수 통제 — 모든 Arm을 같은 출발선에서(고정 프로토콜):**
1. **truncate**: `TRUNCATE telemetry; TRUNCATE device;` — 행수를 0으로 정렬(인덱스 깊이·버퍼풀 드리프트 제거). Arm 간 비교 공정성의 핵심.
2. **fsync 시작 스냅**: `SHOW GLOBAL STATUS WHERE Variable_name IN ('Innodb_data_fsyncs','Innodb_os_log_fsyncs');`
3. **본 측정(램프업 포함 단일 런)**: 박스 `iostat -xzt 1 sda > ~/iostat-<arm>.log` 켜고 → 맥 `k6 ... -e RATES=40,60,80,120,160 telemetry-capacity.js`. **낮은 RATES 초반 단계가 워밍업 역할**(별도 워밍업 런 불필요) — JIT·풀은 앱 재기동 안 했으면 웜 유지, INSERT 측정은 버퍼풀 콜드 영향이 작다. **steady-state 정점만 해석**, 램프 구간 버림.
4. **fsync 끝 스냅** + iostat `Ctrl-C`. 로그 맥으로 scp.
5. 기록: 포화점(req/s), **요청당 fsync** = (data·log 델타 ÷ http_reqs), iostat 정점 f/s·%util.

> **측정 조건 차이(정직 기록)**: A0/A1은 누적 행수(34,987~)에서, **A2~는 truncate 0행 출발**. 영향은 인덱스 드리프트뿐이라 fsync 결론·배수 서사엔 무관. A2/A3/A2-x끼리는 같은 조건이라 정밀 비교 OK, A0/A1과는 비율·메커니즘으로 비교.

> **queue 모드(A2/A3/A2-x) 포화점 신호는 p95가 아니다.** 큐는 즉시 202라 p95가 "큐 넣기 시간"만 잰다. 진짜 포화점 = **`locus.ingest.dropped` 증가(워커가 못 따라감)** + 처리량 plateau + iostat %util. Grafana 큐 메트릭(depth·dropped)을 같이 본다.

각 Arm 가능하면 3회 → 중앙값(단일은 노이즈).

## 5. 예상 결과 (반증 가능하게 미리 적는다)
- A1: 포화점 **수배↑** 예상(fsync 완화가 직접 병목 해소). 클수록 "fsync가 진짜 병목"의 강한 증거.
- A2(크기 200): A1과 비슷~이상 예상, **내구성은 유지**. → "내구성 포기 안 하고도 배치로 포화점↑"이 핵심 결론.
- A2-x: Device upsert 제거 시 추가 상승이면 → 핫패스 UPDATE도 비용. 미미하면 → Telemetry insert가 지배적.
- **만약 포화점이 안 오르면**: 병목이 fsync가 아니라 CPU/풀/네트워크 → Grafana(CPU/HikariCP)로 재귀인. (효과 없던 시도도 솔직히 기록 — §3.1)

## 6. M2~M4로의 연결 (이 실험의 엔지니어링 가치)
- A2가 "그냥 배치(인메모리 큐)"의 포화점과 **한계(앱 크래시 시 버퍼 유실, fan-out 불가, RAM 넘는 백프레셔)**를 숫자로 보여준다.
- fan-out 브로커(Redis Streams, M4)는 포화점을 또 올리는 게 아니라(싱크가 같으면 포화점도 같다) **그 한계를 메우는** 것: Consumer Group fan-out + 앱 크래시 생존 + `XACK`/`XCLAIM` 복구. (Kafka 아님 — 규모상 Redis Streams로 충분, [ADR 0007](../decisions/0007-messaging-storage-redis-streams-and-governance.md).)
- → 한 줄 정리: *"배치만으로 포화점은 이만큼 올랐다(측정). 브로커는 거기에 fan-out·생존을 더한 거지 속도를 산 게 아니다. 그래서 Kafka를 관성적으로 고르는 대신 규모에 맞는 Redis Streams를 골랐고, 못 버티면 Kafka로 전환하는 기준까지 측정으로 잡는다."*

## Before (A0 = M0 baseline, flush=1)
> A0는 변수를 안 바꿨으므로 M0 측정을 그대로 인용([M0.md](M0.md)). 재측정 불필요.

| 지표 | 값 |
|---|---|
| 포화점 | ~33 req/s |
| 요청당 fsync | ~1.2 (log ~1.0 + background) |
| 디스크 f/s · %util · f_await | 39 · 97% · 25ms |
| CPU / HikariCP | 유휴(2~8%) / pending 적체 |

## 변경 + After

### A1 — `innodb_flush_log_at_trx_commit` 1 → 2 (설정만, 코드 0) ✅ 2026-06-29
> 동적 변수(`SET GLOBAL`)라 재시작 없이 전환. 측정 후 1로 복귀.
> 원본: [M1-raw/iostat-A1-rates40-120.log](M1-raw/iostat-A1-rates40-120.log) (포화점 탐색 런), [iostat-A1-rates28-38.log](M1-raw/iostat-A1-rates28-38.log) (저부하 런).

| Arm | 포화점 | log fsync/req | data fsync/req | 디스크 f/s·%util | vs A0 | 메모 |
|---|---|---|---|---|---|---|
| A0 | ~33 | ~1.0 | ~1.2 | 39·97% | — | flush=1 (M0) |
| **A1** | **~66** | **0.05** | 0.40 | 39·96% | **포화점 ~2×** | flush=2 |

- fsync 델타(스냅): data 6216 / log 828 / http_reqs 15434 → **log fsync/req 0.05**(커밋마다 → ~1초마다).
- ⚠️ **측정 위생**: 첫 A1 런은 RATES를 38까지만 밀어 포화점(이미 ~66)을 못 봐서 "효과 없음"으로 오독. RATES=40~120으로 다시 밀어 ~66 확인. → 포화점 탐색은 **충분히 높은 도착률**이 필수.

### A2 — 인메모리 큐 + 배치 적재 (코드, flush=1=내구성 유지) ✅ 2026-06-29
> queue 모드(batch-size=500, max-delay=200ms, device-upsert=true). 도착률을 단계적으로 올려 포화점을 핀 3개 런.
> 원본: [M1-raw/iostat-A2c.log](M1-raw/iostat-A2c.log)(포화 런) 외 A2/A2b.
> queue 모드 포화 신호는 p95(즉시 202라 <2ms)가 아니라 **`locus.ingest.dropped` 증가 + 큐 만석 + 처리량 평탄**.

| 런 | RATES | 달성 처리량 | dropped | 디스크 f/s·%util | 판정 |
|---|---|---|---|---|---|
| A2 | 40~160 | 피크 ~150 | 0 | 38.7·94% | 미포화(선형 추종) |
| A2b | 150~500 | 485 선형 | 0 | 36.6·94% | 미포화 |
| **A2c** | 500~1600 | **피크 1,437** | **78,031** | 34.5·94%·CPU↑0.10 | **포화점 확정** |

| Arm | 포화점 | data fsync/req | vs A0 | 내구성 | 메모 |
|---|---|---|---|---|---|
| **A2** | **~1,437 req/s** | **0.059** (6912÷117969) | **~44×** | **유지(flush=1)** | 적재행 117,969 = 196,000−78,031 |

- **포화점에서 병목 이동 시작**: 디스크 %util 94 유지 + 큐 10,000 만석 + 드롭 폭증 동시(처리량 평탄 직후). CPU가 처음으로 ~0.10까지 상승(이전 전 런 2~8%) — 디스크가 여전히 주 병목이나 배치가 fsync 예산을 거의 다 짜냄.
- **자기조절 배치**: 도착률↑ → drainTo가 더 크게 묶음 → fsync/req가 1.2(A0)→0.48(A2@160)→0.14(A2b@500)→0.059(A2c 포화)로 감소.

### A2-x — device upsert 격리 (`device-upsert=false`, 나머지 A2c 동일) ✅ 2026-06-29
> A2c와 같은 RATES(500~1600)·조건. device upsert만 끔. 원본: [M1-raw/iostat-A2x-deviceupsert-off.log](M1-raw/iostat-A2x-deviceupsert-off.log).

| Arm | 포화점 | 드롭 | data fsync/req | 디스크 f/s·%util |
|---|---|---|---|---|
| A2c (upsert ON) | 1,437 | 78,031 | 0.059 (6912÷117969) | 34.5·94% |
| **A2-x (upsert OFF)** | **1,433** | 53,161 | 0.045 (6489÷142839) | 35.0·94% |

- **device upsert는 포화점에 사실상 영향 없음**(1,437→1,433). batched upsert(배치당 디바이스 1회 dedup)가 충분히 싸서 교란이 거의 없었음을 확인. fsync는 ~6%만 감소(device 쓰기 제거분).
- "교란변수 의심 → 측정 → 거의 교란 없음" 격리 완료. 텔레메트리 insert가 지배적.

### A3 — 배치 + flush=2 합산 (`SET GLOBAL ...=2`, 나머지 A2c 동일) ✅ 2026-06-29
> A2c와 같은 RATES·조건 + flush=2. 측정 후 1로 복귀. 원본: [M1-raw/iostat-A3-batch-flush2.log](M1-raw/iostat-A3-batch-flush2.log).

| | A2c (배치, flush=1) | A3 (배치, flush=2) |
|---|---|---|
| 포화점 | 1,437 | **1,418** (사실상 동일) |
| 드롭 | 78,031 | 58,661 |
| data fsync/req | 0.059 | 0.0485 |
| **log fsync/req** | 0.015 | **0.0058** |
| 디스크 f/s·%util | 34.5·94% | 34.5·89% |

- **배치 위에 flush=2를 더해도 포화점이 안 오름**(1,437→1,418, 노이즈). flush=2가 log fsync/req는 더 줄였지만(0.015→0.006) 처리량 무변 → **배치 후 redo 로그 fsync는 더는 병목이 아니다.** 남은 제약 = data fsync(doublewrite·페이지 플러시, ~35/s), 이건 커밋 횟수 무관이라 배치·flush 둘 다 못 줄임 = 이 HDD의 바닥.
- **설계 함의**: 배치하면 내구성 포기(flush=2)가 처리량을 0만큼 올림 → **내구성 유지(A2, flush=1)가 최종.** 공짜 이득 없는데 안전 버릴 이유 없음(측정 기반 결정).
- **flush 상태 검증**: A2c log fsync(1,781) > A3(796) — flush=1(커밋마다)이 flush=2(드물게)보다 많음과 일치 → **A2 측정들은 flush=1이었음을 데이터로 확인**(내구성 유지 서사 안전).

## 해석
- **병목 = fsync 확정(인과)**: 요청당 fsync를 줄이면 포화점이 비례 상승. A1(설정, 1.2→0.4)에서 33→66, A2(배치, →0.059)에서 33→**1,437**. `log fsync/req` 1.0→0.05(A1)가 직접 증거.
- **A2가 결론 — 내구성 유지하며 ~44×**: 같은 HDD·같은 fsync 예산(~35/s)인데 배치로 요청당 fsync를 1.2→0.059(20배↓) → 처리량 33→1,437(44배↑), **flush=1 그대로**. A1(flush=2, 내구성 포기)이 66이었던 것 대비 **내구성 유지하고도 A1의 22배**. M1 가설("fsync를 모아 줄이면 디스크 교체 없이 적재 수십 배")이 측정으로 닫힘.
- **A1은 진단용**: flush=2는 정전 시 ~1초 커밋 손실이라 최종 설계 아님. 최종 = A2(배치).
- **A3 — 배치 후엔 flush 무의미**: 배치+flush=2(A3)가 배치+flush=1(A2c)와 동일 포화점(1,418 vs 1,437). 배치가 이미 커밋 fsync를 다 흡수해 redo 로그가 더는 병목이 아님. 남은 바닥 = data fsync(~35/s). → **내구성 포기로 얻을 게 없어 A2(flush=1)를 최종 채택**(측정 기반 결정).
- **A2-x — device upsert는 교란 아님**: 끄나(1,433) 켜나(1,437) 포화점 동일. batched upsert가 싸서 교란 거의 0. 텔레메트리 insert가 지배적.
- **포화점에서 병목 이동 조짐**: 모든 A2 런에서 포화점 부근 CPU가 처음 ~0.10~0.15까지(이전 2~8%). 디스크가 여전히 주 병목이나, 다음(M2/M7)에서 이 이동을 측정으로 추적.
