# M1 — 적재 천장 깨기: fsync 분할 실험 (설계서)

> **상태: 설계 완료 / 측정 대기**(집 LAN 박스 필요). 집 가면 아래 표만 채운다.
> M0에서 잡은 병목(`단건 insert + 커밋당 HDD fsync → ~33 req/s 천장`)을 **MySQL 안에서 먼저 짜낸다.**
> 외부 브로커는 여기서 안 쓴다 — 이 실험이 "왜 그냥 배치로 안 끝나고 브로커가 필요한가(= fan-out/생존)"의 답을 측정으로 만들어 준다. 브로커 = Redis Streams(M4), Kafka 아님([ADR 0007](../decisions/0007-messaging-storage-redis-streams-and-governance.md)).

---

## 0. 질문 한 줄
**fsync를 줄이면 적재 천장이 어디까지 올라가나, 그리고 그게 디스크 바운드라는 증거를 어떻게 확증하나.**

## 1. 가설 (M0에서 이어짐)
- 현재 경로: 요청 1건 = `@Transactional` 1개 = **커밋 1번 = fsync ≥1번**. 천장 ~33 req/s.
- 5400rpm HDD 랜덤 IOPS ~75 → 커밋당 fsync 여러 번(redo + doublewrite 등) + Device upsert UPDATE가 겹쳐 ~33로 떨어진 것으로 **추정**. 실측으로 확인한다.
- **fsync 횟수를 줄이는 두 축**:
  - (a) **여러 줄을 한 트랜잭션에** 묶는다(배치/벌크 insert) → fsync 1번이 N줄 커버.
  - (b) **커밋당 fsync 자체를 줄인다**(`innodb_flush_log_at_trx_commit` 완화) → 내구성↔처리량 트레이드오프.

## 2. 결정적 증거 지표 (smoking gun)
숫자 없으면 개선이 아니다. 천장(req/s)만 보지 말고 **fsync/req**를 직접 잰다:
- `SHOW GLOBAL STATUS LIKE 'Innodb_data_fsyncs'` 의 **델타 / 처리한 요청 수** = **요청당 fsync 횟수**.
- 이게 줄어드는 만큼 천장이 오르면 → "병목은 fsync였다"가 **증명**된다(상관이 아니라 인과).
- 보조: 박스 `iostat -x 1`의 디스크 `%util`(100%→탈출), `Innodb_os_log_fsyncs`, MySQL `Com_commit` 레이트.

## 3. 비교군 — 한 번에 한 변수만 (계획서 §3.1)
모두 같은 부하(`telemetry-capacity.js`, 1Hz 디바이스 ramping-arrival)로 knee를 잰다.

| Arm | 변경 | 내구성 | 코드/설정 | 의도 |
|---|---|---|---|---|
| **A0** | 현재 단건 insert(@Transactional/req) | 안전(flush=1) | 변경 없음 | **Before**(= M0 천장 재확인) |
| **A1** | `innodb_flush_log_at_trx_commit=2` | 약함(정전 시 ~1s 손실) | DB 설정만, 코드 0 | 커밋당 fsync 비용만 분리 측정 |
| **A2** | 앱 배치 적재(버퍼 N건 → 한 tx, JDBC batch) | 안전(flush=1) | 코드 변경 | "그냥 배치"만으로 어디까지 |
| **A3** | A2 + `flush=2` 결합 | 약함 | 코드+설정 | 두 축 합산 상한 |
| **A2-x** | A2에서 **Device upsert 분리/제거** | 안전 | 코드 변경 | 교란변수(핫패스 UPDATE) 영향 격리 |

> **교란변수 주의:** 현재 `ingest()`는 트랜잭션 안에서 Device upsert(`findByDeviceId` + `save`=UPDATE)를 **매 요청** 한다. Telemetry insert만의 효과를 보려면 A2-x로 분리한다(예: upsert를 비동기/주기 배치로, 또는 풀이 2000이라 디바이스별 1회만 INSERT되게).

### A2 구현 메모 (집 가서 코딩할 때)
- HTTP는 지금처럼 **202 즉시 응답**(컨트롤러 주석에 이미 "M2 비동기 큐 전환과 호환"). 수신 → 인메모리 큐(`BlockingQueue`) → 주기/크기 트리거 flush 워커가 **한 tx로 N건 saveAll**.
- **JDBC 배치가 실제 멀티로우로 나가려면** datasource URL에 `rewriteBatchedStatements=true` 필수(없으면 N번 왕복 — 네트워크 절감 0). Hibernate `hibernate.jdbc.batch_size=N`, `order_inserts=true`.
- flush 트리거 2변수: **배치 크기**(예 50/200/500)와 **최대 지연**(예 50ms/200ms). 크기↔지연↔처리량 곡선을 그린다.
- **유실 위험**: 인메모리 큐는 앱 크래시 시 버퍼 손실 → 이게 정확히 fan-out 브로커(Redis Streams, M4 — 별도 프로세스라 앱 크래시 생존 + `XPENDING`/`XCLAIM` 복구)가 사는 지점. A2의 한계로 **명시 기록**한다.

## 4. 측정 절차
2-머신(박스 SUT + 맥 부하/관측)은 [RUNBOOK.md](RUNBOOK.md). 각 Arm마다:
1. 박스 재기동 + 테이블 truncate(또는 행수 기록), `SHOW GLOBAL STATUS` 스냅샷.
2. 맥: `k6 run -e BASE_URL=http://박스IP:8093 -e RATES=20,30,40,60,80,120 load/telemetry-capacity.js`
3. 박스: `iostat -x 1` + `mysqladmin ext -i1 | grep -E 'fsync|commit'` 동시 기록.
4. knee(plateau/`dropped_iterations`/p95 급등)에서 멈춘 req/s, p95, %util, **fsync/req** 기록.
5. 같은 Arm 3회 → 중앙값(단일은 노이즈).

## 5. 예상 결과 (반증 가능하게 미리 적는다)
- A1: 천장 **수배↑** 예상(fsync 완화가 직접 병목 해소). 클수록 "fsync가 진짜 병목"의 강한 증거.
- A2(크기 200): A1과 비슷~이상 예상, **내구성은 유지**. → "내구성 포기 안 하고도 배치로 천장↑"이 핵심 .
- A2-x: Device upsert 제거 시 추가 상승이면 → 핫패스 UPDATE도 비용. 미미하면 → Telemetry insert가 지배적.
- **만약 천장이 안 오르면**: 병목이 fsync가 아니라 CPU/풀/네트워크 → Grafana(CPU/HikariCP)로 재귀인. (효과 없던 시도도 솔직히 기록 — §3.1)

## 6. M2~M4로의 연결 (이 실험의 프로젝트 가치)
- A2가 "그냥 배치(인메모리 큐)"의 천장과 **한계(앱 크래시 시 버퍼 유실, fan-out 불가, RAM 넘는 백프레셔)**를 숫자로 보여준다.
- fan-out 브로커(Redis Streams, M4)는 천장을 또 올리는 게 아니라(싱크가 같으면 천장도 같다) **그 한계를 메우는** 것: Consumer Group fan-out + 앱 크래시 생존 + `XACK`/`XCLAIM` 복구. (Kafka 아님 — 규모상 Redis Streams로 충분, [ADR 0007](../decisions/0007-messaging-storage-redis-streams-and-governance.md).)
- →  답: *"배치만으로 천장은 이만큼 올랐다(측정). 브로커는 거기에 fan-out·생존을 더한 거지 속도를 산 게 아니다. 그래서 Kafka 반사 대신 규모에 맞는 Redis Streams를 골랐고, 못 버티면 Kafka로 전환하는 기준까지 측정으로 잡는다."*

## Before (A0 = M0 baseline, flush=1)
> A0는 변수를 안 바꿨으므로 M0 측정을 그대로 인용([M0.md](M0.md)). 재측정 불필요.

| 지표 | 값 |
|---|---|
| 포화점(knee) | ~33 req/s |
| 요청당 fsync | ~1.2 (log ~1.0 + background) |
| 디스크 f/s · %util · f_await | 39 · 97% · 25ms |
| CPU / HikariCP | 유휴(2~8%) / pending 적체 |

## 해석
- **병목 = fsync 확정(인과)**: 요청당 fsync를 1.2→0.4로 줄였더니 포화점이 33→66으로 **비례 상승**. `log fsync/req` 1.0→0.05가 직접 증거.
- **A1의 한계 = 내구성**: flush=2는 정전 시 ~1초 커밋 손실. 진단용이지 최종 설계 아님.
- **남은 바닥**: %util은 96으로 여전히 포화 — background fsync(doublewrite·페이지 플러시)가 새 제약. fsync를 더 줄이려면 **요청당 커밋 수 자체를 줄이는 배치(A2)**가 필요.
- **다음**: A2(인메모리 큐+배치)로 **내구성 유지하며** 같은 천장 상승을 내는지 측정 → M2 정당화.
