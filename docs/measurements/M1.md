# M1 — 적재 포화점 높이기: fsync 분할

> 상태: **측정 완료(2026-06-29)**. 트리거: [M0.md](M0.md). 후속 과제: [M2.md](M2.md) 저장소 순차화.
> 증거: 원본 [M1-raw/](M1-raw/)(arm별 iostat). 배치의 유실 한계 → M4 Redis Streams([ADR 0007](../decisions/0007-messaging-storage-redis-streams-and-governance.md)).

## 목표
요청당 fsync를 줄여 포화점을 올린다. 동시에 "병목 = fsync"를 인과로 확정한다. MySQL 안에서 개선하고, 외부 브로커는 쓰지 않는다.

## 문제 상황
포화점 ~33은 커밋당 fsync가 묶는다. 요청 1건 = 커밋 1번 = fsync ≥1번이고, 5400rpm HDD의 fsync가 직렬(f_await ~25ms)이라서다. fsync를 줄이는 축은 둘이다: 여러 줄을 한 트랜잭션에 묶는 배치, 커밋당 fsync를 완화하는 `innodb_flush_log_at_trx_commit`(내구성 트레이드오프).

## 해결 과정 (요약)
1. **flush=2로 33 → 66 (2배)** — 커밋당 fsync 비용만 분리. fsync가 직접 병목임을 시사.
2. **배치로 33 → 1,437 (44배), 내구성 유지** — 요청당 fsync 1.2 → 0.059.
3. **배치 후 flush·device는 무의미** — A3(배치+flush=2), A2-x(device off) 모두 무변.

## 해결 과정 (상세)

### 1. 요청당 fsync를 줄이면 포화점이 오른다 (인과)
포화점은 요청당 fsync가 정한다. 결정 지표는 포화점 단독이 아니라 요청당 fsync다. 같은 부하로 arm별 두 값을 재면 반비례가 나온다:

| Arm | 변경 | 포화점 | 요청당 fsync | 내구성 | vs A0 |
|---|---|---|---|---|---|
| A0 | 단건 insert, flush=1 (= M0) | ~33 | ~1.2 (log ~1.0) | durable | 기준 |
| A1 | `flush=2` (설정만) | **~66** | log **0.05** | 약함(정전 시 ~1s) | 2배 |
| A2 | 배치 적재, flush=1 | **~1,437** | data **0.059** | **durable** | **44배** |
| A3 | 배치 + flush=2 | ~1,418 | data 0.049 | 약함 | (무변) |
| A2-x | 배치, device upsert off | ~1,433 | data 0.045 | durable | (교란 없음) |

요청당 fsync가 1.2 → 0.05 → 0.059로 줄자 포화점이 33 → 66 → 1,437로 올랐다. fsync가 병목이라는 인과 증거다.

<details><summary>측정 프로토콜 · 명령어 (모든 arm 공통)</summary>

```bash
# 1) 변수통제: arm 전 행수 0 정렬
mysql> TRUNCATE telemetry; TRUNCATE device;
# 2) fsync 시작 스냅
mysql> SHOW GLOBAL STATUS WHERE Variable_name IN ('Innodb_data_fsyncs','Innodb_os_log_fsyncs');
# 3) 박스 디스크 캡처 + 맥 부하(충분히 높은 RATES로 포화점까지)
box$  iostat -xzt 1 sda > ~/iostat-<arm>.log
mac$  k6 run -e BASE_URL=http://<박스IP>:8093 -e RATES=40,60,80,120,160 load/telemetry-capacity.js
# 4) fsync 끝 스냅 → 요청당 fsync = (data·log 델타 ÷ http_reqs)
# arm 설정: A1/A3 = SET GLOBAL innodb_flush_log_at_trx_commit=2 (측정 후 1 복귀)
#          A2~ = queue 모드(batch-size=500, max-delay=200ms), A2-x = device-upsert=false
```
queue 모드(A2~) 포화 신호는 p95(즉시 202)가 아니라 `locus.ingest.dropped` 상승 + 큐 만석 + 처리량 평탄이다. 각 arm 가능하면 3회 중앙값.

### 2. 배치가 최종 — 내구성 유지하며 44배
최종안은 배치(A2)다. 내구성을 유지하며(`flush=1`) 포화점을 44배로 올린다. 같은 HDD·같은 fsync 예산(~35/s)에서 요청당 fsync를 1.2 → 0.059로 줄인 결과다. A1(flush=2)이 66이었던 것과 비교하면 내구성을 유지하고도 A1의 22배다. A1은 진단용일 뿐 최종안이 아니다(정전 시 ~1s 커밋 손실).

- 배치는 자기조절한다. 도착률이 오르면 `drainTo`가 더 크게 묶어 요청당 fsync가 1.2 → 0.48(@160) → 0.14(@500) → 0.059(포화)로 줄어든다.
- 포화 순간 큐 10,000 만석 + 드롭 폭증 + CPU가 처음으로 ~0.10까지 상승(이전 2~8%). 디스크가 여전히 주 병목이나 배치가 fsync 예산을 거의 다 소진했다.

### 3. 격리 — 배치 후 flush·device upsert는 무의미
배치 후에는 flush 완화도 device upsert도 포화점을 못 바꾼다.

- **A3(배치+flush=2)**: 1,437 → 1,418(무변). flush=2가 `log fsync/req`는 더 줄였으나(0.015→0.006) 처리량은 그대로다. 배치가 이미 커밋 fsync를 흡수해 redo 로그는 병목이 아니다. 남은 바닥 = data fsync(doublewrite·페이지 플러시, ~35/s), 커밋 횟수와 무관이라 배치·flush 둘 다 못 줄인다. 내구성 포기로 얻을 게 없어 A2(flush=1)를 최종 채택한다.
- **A2-x(device upsert off)**: 1,437 → 1,433(무변). 배치당 device 1회 dedup upsert가 싸서 교란이 거의 없다. 텔레메트리 insert가 지배적이다.

## 성과와 다음 단계
**성과**
- 병목 = fsync를 인과로 확정. 요청당 fsync를 줄이면 포화점이 비례 상승(A1·A2).
- 내구성 유지하며 포화점 33 → 1,437 (약 44배). 디스크 교체 없이 배치만으로, `flush=1` 그대로.
- 격리로 최종안 확정. 배치 후 flush 완화·device upsert 분리는 무의미.

**다음 단계**
- **M2**: 남은 바닥(data fsync = InnoDB B-tree 랜덤 쓰기)을 순차 쓰기(TimescaleDB)로 바꿔 포화점을 더 올린다. → [M2.md](M2.md).
- **M4**: 배치(인메모리 큐)는 앱 크래시 시 큐·드롭을 유실하고 fan-out을 못 한다. 별도 프로세스 브로커(Redis Streams)가 이를 메운다. 브로커는 포화점을 더 올리는 게 아니라(싱크가 같으면 포화점도 같다) fan-out·생존을 더한다. Kafka가 아니라 규모에 맞는 Redis Streams([ADR 0007](../decisions/0007-messaging-storage-redis-streams-and-governance.md)).

| 지표 | 정의 | 판정 |
|---|---|---|
| 요청당 fsync | `Innodb_data_fsyncs`·`_os_log_fsyncs` 델타 ÷ http_reqs | 결정 지표 — 줄면 포화점↑ |
| 포화점 | 처리량 plateau (req/s) | queue 모드는 `dropped` 상승으로 판정 |
| 디스크 | iostat f/s · %util · f_await | 병목 확증(~35 f/s·94% 유지) |

> 절대수치는 이 HDD 종속 → before/after **비율**로 해석.

## 폐기한 시도와 교정한 가설
- **A1 첫 런에서 "효과 없음"으로 잘못 판단**: RATES를 38까지만 밀어 이미 ~66이던 포화점을 못 봤다. RATES=40~120으로 다시 밀어 ~66 확인. 포화점 탐색은 충분히 높은 도착률이 필요하다.
- **배치 후 flush=2 기대 → 무의미로 확인**: A3가 A2와 동일 포화점(1,418 vs 1,437). 내구성을 포기해도 처리량이 0만큼 오르므로 폐기. flush 상태 검증: A2c log fsync(1,781) > A3(796)로 A2 측정이 `flush=1`이었음을 데이터로 확인.
- **device upsert 교란 의심 → 격리 후 무교란**: A2-x(1,433)와 A2c(1,437) 동일. batched dedup upsert가 싸서 교란이 거의 없다.
