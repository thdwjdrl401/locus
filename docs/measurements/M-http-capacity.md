# M-http-capacity — HTTP 수집 경로 인입 최대 처리량 (CPU 바운드 규명)

> 상태: **박스 측정 완료(2026-07-08).** 트리거: M-MQTT가 HTTP 최대 처리량을 "k6(Colima) 한계 / 스토리지 ~9.7K"로 귀속했는데([M-MQTT.md §최대 처리량](M-MQTT.md)), 그 귀속이 부정확했음을 이 측정이 정정한다.
> 결론: **HTTP 인입 최대 처리량을 제한하는 것은 스토리지가 아니라 박스 CPU다.** 코어 핀 6→8로 12K→16K 선형 확장(+33%)으로 확증. 지배분은 앱 요청 처리(역직렬화·검증·매핑·enqueue).

## 환경
- SUT: `i7-6700HQ 4c/8t · 8GB · 5400rpm HDD`. 앱 힙 `-Xms/-Xmx=1500m` G1GC.
- 저장: TimescaleDB(docker) · Redis · Mosquitto. 앱은 호스트 JVM 직접 실행(`scripts/run-app.sh`).
- 앱 설정(고정): `INGEST_MODE=queue INGEST_WORKERS=4 INGEST_QUEUE_CAPACITY=200000 INGEST_DEVICE_UPSERT=true DB_POOL_MAX=20`, `server.tomcat.threads.max=300`.
- 부하: 맥(`.102`)에서 k6 `load/telemetry-fleet.js` — **1 VU = 1 디바이스(고정 deviceId)·지속 커넥션·1Hz**. 스윕 `DEVICES=4000,8000,12000,16000,20000`, 각 단계 30s 램프+90s 유지.
- 관측: 맥 Prometheus/Grafana(박스 `8093/actuator/prometheus` + node-exporter `9100`). 대시보드 throughput·CPU·HikariCP·디스크.
- **측정 위생**: 핀6 baseline은 `docker compose down -v` 후 fresh 볼륨. 핀6→핀8 사이엔 리셋 안 함 — 핀8이 핀6의 데이터를 물고도 더 높은 처리량이라 **+33%는 보수적**(리셋했으면 더 벌어질 수 있음). 누적 청크/autovacuum 오염은 아래 교란변수.

## 부하 모델을 왜 바꿨나 (telemetry-capacity → telemetry-fleet)
기존 `telemetry-capacity.js`(ramping-arrival-rate)는 **총 도착률**만 통제하고 deviceId는 `i%POOL`로 회전, 커넥션은 maxVUs로 고정한다. "N대의 1Hz 디바이스"가 아니다(디바이스별 주기·연결 미통제). MQTT 벤치(`1 client=1 device=1Hz`)와 apples-to-apples가 안 된다.
`telemetry-fleet.js`는 **VU=디바이스**인 닫힌 루프로, 고정 deviceId가 지속 커넥션 하나로 매초 1건 발행하고, 서버가 느려지면 실제 폰처럼 1Hz에서 밀린다(`device_period_ms`·`behind_schedule`로 관측). 이게 함대 capacity의 올바른 모델이다.

## 부하로 드러난 한계
스윕에서 디바이스 수를 올리면 어느 단계까지는 서버 req/s가 디바이스 수를 따라가다가(1Hz 유지), 특정 지점에서 정체·붕괴한다. 그 정체 지점이 이 경로의 함대 상한(knee)이고, 그때 어느 자원이 서는지가 병목이다.

## Before — 코어 핀 0–5 (6 논리코어, 기존 baseline 조건)
`scripts/run-app.sh`가 `taskset -c 0-5`로 앱을 6코어에 고정(코어 6–7은 OS/시스템 예약). fresh 볼륨 스윕:

| 디바이스 | 서버 req/s | 앱코어(0–5) | 서버 처리시간 | 판정 |
|---|---|---|---|---|
| 4k | ~4,000 | 65% | 4ms | 1Hz 유지 |
| 8k | ~8,000 | 78% | 7ms | 1Hz 유지 |
| **12k** | **~12,186 (peak)** | **~90%** | 12–24ms | 거의 유지 — **knee** |
| 16k | ~7,000–9,000 (하락) | 90→78% | 15ms | 붕괴 |
| 20k | ~7,000→0 | 붕괴 | — | 붕괴 |

- knee ≈ **12k 디바이스 / ~12,186 req/s**. 그 지점 **앱 코어 0–5가 ~90%**.
- **서버 처리시간은 끝까지 ≤24ms로 낮았다** — 요청 처리는 빠른데 CPU가 동나 더 못 받은 것(느려서가 아님).
- CPU 분해(박스 8코어 대비): **JVM(앱) ~44%(≈3.5코어) > DB+OS ~28%(≈2.2코어)**. 앱 요청 경로가 지배분.
- 스토리지·풀은 여유: 디스크 %util ~68%, HikariCP pending 0(DB 커넥션 대기 없음), DB inserted가 인입과 균형(drop 0).
- 16k·20k에서 처리량이 12k보다 **떨어진다** = 박스가 아니라 **맥 부하도구 포화**(아래 참조).

## 변경 내용 — 코어 핀 해제 0–7 (8 논리코어)
CPU가 병목인지 확증하려 앱을 8코어 전부로 실행(`taskset -c 0-7`, 나머지 flag 동일). 다른 변수는 고정. 같은 스윕 재측정.

## After — 코어 핀 0–7
| 디바이스 | 서버 req/s | 박스 CPU(8코어) | 판정 |
|---|---|---|---|
| 4k | ~4,000 | — | 유지 |
| 8k | ~8,000 | — | 유지 |
| 12k | ~12,000 | — | 유지 |
| **16k** | **15,000–16,118 (peak)** | 8코어 **~75%** (총 71%) | 거의 유지 — **knee 이동** |
| 20k | ~13,000 (하락) | — | 붕괴(맥/디스크) |

- **peak 16,118 req/s, knee 12k→16k.** 코어 6→8(+33%)에 처리량 12k→16k(+33%) — **선형 확장 = CPU 바운드 확증.**
- knee에서 박스 CPU **~71%(8코어 각 ~75%)로 여유** 생김. JVM ~51%(≈4.1코어), DB+OS ~20%(≈1.6코어).
- 20k에서 ~13k로 하락 = 이제 위쪽 한계가 **맥 부하도구**(16k+ 커넥션에서 포화)로 이동. 디스크도 ~80%로 상승.

## 양단 CPU 관측 (병목 위치 확정)
| 단계 | 맥(부하도구) idle | 박스 앱코어 |
|---|---|---|
| 4k–8k | 65–70% (여유) | 65–78% |
| 12k | ~50% (여유) | ~90% (핀6) |
| 16k–20k | **0–4% (포화, sys 74%)** | ~75% (핀8) |

- **핀6 knee(12k)에선 맥이 여유(idle 50%)·박스 코어 포화(90%)** → 병목이 박스 CPU임이 분명.
- **16k+에선 맥이 커널/네트워크(sys 74%)로 포화** → 그 위 붕괴는 부하도구 한 대의 한계.

## 초기 측정을 오도한 교란변수 4개 (정정 기록)
초기 런(단일 20k 스텝, `down -v` 전)은 ~10K·서버 처리시간 22ms로 보였다. 이 값은 아래가 **동시에 얽혀** 나온 것이라 오도했고, 각각을 격리한 뒤에야 깨끗한 신호가 드러났다. **CPU 결론 자체는 이것들과 무관한 핀 6→8 실험으로 확정되므로 안 흔들린다.** 초기 22ms→fresh 10ms는 단일 원인으로 깔끔히 귀속되지 않는다(아래 1·2가 섞임).

1. **부하 프로파일(가장 컸다).** 단일 20k 스텝은 맥을 즉시 포화시켜 처리량이 맥 한계(~10K)로 붕괴 → 박스의 12K knee를 못 드러냄. 단계별 스윕으로 비로소 knee가 보였다. 초기 ~10K는 박스 한계가 아니라 붕괴값.
2. **누적 DB 상태.** `down -v` 없이 반복 버스트 → 체크포인트·autovacuum 부채가 단일 HDD에서 flush와 경합 + 버스트 후 정착 꼬리(디스크 99% 스톨, ~90s). 단 그 구간 디스크는 37–56%로 **포화 아님** → 이건 거들었지 초기 저처리량의 주범은 아님. `down -v`로 제거.
3. **부하도구 co-location.** 박스에서 k6를 같이(도커·localhost) 돌리면 앱과 CPU·디스크 경합 → 3천 VU에서 전멸(0 complete). 부하는 맥에서만.
4. **맥 한 대.** 16k+ 지속 커넥션에서 부하도구가 먼저 포화(sys 74%) → 유효 처리량 붕괴. 이 붕괴가 박스 한계로 오인됐다(M-MQTT의 "HTTP ~10K"이 이 붕괴/도구-포화 구간).

## 다른 것은 병목이 아님 (반증 기록)
- **Tomcat 워커 스레드**: `threads.max` 300→600, 처리량 무변(~11K)·지연 악화(22→50ms)·CPU 상승. jstack: http-nio 워커가 작업 큐에서 idle(producer는 논블로킹 `offer`). 스레드 아님.
- **인입 큐 락 / consumer(DB)**: `ArrayBlockingQueue` 단일락 의심했으나 consumer 여력(배치 500×4워커÷170ms flush ≈ 11.7K rows/s) > 달성 인입, drop 0. DB 아님.
- **Poller 단일코어**: 코어별 CPU 균등(0–5 고르게 ~78–90%), 단일코어 포화 없음. Poller 아님.

## 해석
- **HTTP 인입 최대 처리량의 제한 = 박스 CPU(요청당 앱 처리 비용).** 스토리지·스레드·큐락·Poller 전부 반증. 이 경로 CPU 한계: 핀6 ~12K·핀8 ~16K req/s. 앱 요청당 CPU ≈ 3.5–4코어 ÷ 12–16K ≈ **~0.25–0.3ms/요청**(JSON 역직렬화 + 검증 + 봉투→도메인 매핑 + enqueue).
- **M-MQTT의 HTTP 귀속 정정**: 그때 "HTTP ~10K = k6 한계 / 스토리지 9.7K"는 붕괴·도구-포화 구간 값이었다(단일 고부하 → 부하도구 포화). 실제 박스 한계는 CPU 바운드 ~12K(핀6)로 더 높다.
- **남은 한계 / 다음 병목**: 16K 위는 (a) 부하 머신 2대+로 맥 한계 제거 후 (b) 박스 CPU(핀8 75%)와 디스크(~80%) 중 뭐가 먼저 서는지 본다. 하드웨어 추가 없이 넘기려면 **앱 핫패스 CPU 절감**(프로파일로 지점 확정 후 파싱/검증 경량화)이 유일한 지렛대다. 여기 디스크 ~80%는 **처리량이 높아서 순간적으로 그런 것**이지 데이터 성장에 따른 열화가 아니다 — 지속·대용량 적재는 5분 청크 + 12h retention으로 평평 유지가 [M2-par](M2-par.md)에서 측정됨(63분 10k 무손실).
- **비교 가능성**: 핀 해제(0–7)는 기존 마일스톤(전부 0–5 핀)과 apples-to-apples 아님. 별도 라벨 실험으로만 유효(앱이 DB·OS와 전 코어 겹쳐 써 노이지).
