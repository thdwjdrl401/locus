# M2-par — 배치 워커 병렬화 + 적재 무손실 용량 (단일 HDD 10k)

> 상태: **측정 완료(2026-07-01)**. 결과: 단일 워커 5,459 → 워커 병렬화로 group commit 스케일(append-only ~14k), device 행 락이 둘째 병목(append-only식 워커 스케일을 막음), append-only 경로에서 큐 사이징으로 **도착 10,000 rows/s 무손실(dropped/s=0)** 달성. (device-on은 10k에서 큐 200k가 가득 차고 드롭 = drain < 10k 지속 deficit → 10k엔 device 분리가 필수.)
> 트리거 측정: [M2.md](M2.md). 후속 과제: device 상태 분리 = M4 Redis 최신상태 캐시.

## 0. 질문 한 줄
**M2에서 병목이 단일 배치 워커로 이동했다. 워커를 병렬화하면 포화점이 SLO(10k)까지 오르는가, 다음 병목은 어디로 가는가, 그리고 10k를 *무손실*로 적재할 수 있는가.**

## 1. 가설
- M2: 디스크가 59% 여유인데 단일 스레드 워커가 직렬 처리율로 막아 5,459에서 포화. 워커 N개로 병렬화하면 디스크 여유를 채워 처리량이 오를 것.
- 반증 가능: 워커를 늘려도 안 오르면 병목이 워커가 아니라 다른 곳(디스크 대역폭·락 경합·CPU).

## 2. 결정적 증거 지표 (node_exporter / Micrometer → Grafana)
- **포화점**(rows/s) = `locus_ingest_inserted_total` rate의 지속 plateau. 램프 피크 Stat은 노이즈라 *평탄 부하의 유지값*으로 판정.
- **드롭**은 `dropped/s`(**카운터**)로 판정. 큐 깊이는 게이지라 스크레이프 간격(~15s) 사이의 짧은 스파이크를 놓침 — 드롭이 있는데 큐 패널이 낮게 보이는 이유.
- **디스크**: %util · 평균 쓰기 크기 · 쓰기 지연 · IOPS. **CPU·HikariCP·GC**로 앱측 병목 배제.

## 환경
- **박스(SUT)**: i7-6700HQ 4c/8t, 8GB, 5400rpm HDD. `taskset -c 0-5` + `-Xmx1500m`. DB·스키마는 [M2.md](M2.md)와 동일(TimescaleDB 2.17.2-pg16, durable).
- **손잡이**: `INGEST_WORKERS`(워커 스레드 수), `DB_POOL_MAX`(HikariCP), `INGEST_DEVICE_UPSERT`(핫패스 device upsert on/off), `INGEST_QUEUE_CAPACITY`(큐 용량).
- **부하**: 맥 → 박스, k6 `load/telemetry-capacity.js`. 천장 탐색은 **평탄 과포화**(도착률 > 천장 고정), 무손실 검증은 **평탄 SLO값**(도착률 = 10,000 고정, 5분).

## 변경 내용
- `TelemetryBatchWorker` 단일 스레드 → `INGEST_WORKERS`개 스레드. 공유 큐에서 각자 `drainTo`, 워커당 커넥션 1개. HikariCP pool ≥ 워커 수.
- 기본값 `workers=1`이라 M2 동작 보존.

## A. 워커 병렬화 — group commit 스케일링
append-only(device upsert off) 평탄 과포화, 워커 수별 지속 처리율:

| 워커 | 적재(지속) | 디스크 %util |
|---|---|---|
| 6 | ~9,500 | ~100% |
| 12 | ~12,800 | ~100% |
| 16 | ~14,400 | ~100% |

- 처리량이 워커↑로 오른다. 기전 = **group commit(그룹 커밋)**: 동시 커밋 트랜잭션이 많을수록 WAL fsync가 한 번에 더 많이 묶여 fsync당 처리율이 오른다. 디스크 %util은 100%지만 평균 쓰기 크기가 커져(순차) 실제 대역폭은 여유.
- → 단일 워커 병목은 병렬화로 해소. 단, 천장은 디스크의 순차 WAL 대역폭으로 수렴(N=16 ~14k).

## B. device upsert = 둘째 병목 (행 락 경합)
정상 경로(device upsert on)는 워커를 늘려도 ~9k에 막히고, N=12에서는 **디스크 %util이 80%로 내려가며 처리량이 역행**(~9k)한다 — 자원 포화가 아니라 **직렬화 신호**.

| N=12 | 적재 | 디스크 |
|---|---|---|
| device-on | ~9,000 | 80% (놀고) |
| device-off | ~12,800 | ~100% (재포화) |

- 토글로 격리: device UPDATE만 끄니 같은 N=12에서 9k→12.8k + 디스크 재포화 → **device 행 락이 append-only식 워커 스케일을 막는다** 확정. device 풀이 2,000행뿐이라 다중 워커가 같은 핫 행을 두고 직렬로 줄 섬(+ 죽은 튜플 폭증으로 device 테이블 autovacuum이 `pg_stat_user_tables`에서 398회 대 telemetry 0회).
- **데드락**: 다중 워커 device upsert가 도착순(LinkedHashMap)으로 행 락을 엇갈리게 잡아 `deadlock detected` → 배치 유실 → N=8이 6,645로 역행. `TreeMap`으로 device_id 정렬 → 모든 워커 동일 락 순서 → 순환 대기 불가로 수정(자원 전순서 기법).
- **device 분리가 10k에 *필수*임을 측정으로 확인**: device-on + 큐 200k + N=6 @ 도착 10k → **큐가 200,000 전체를 채우고 드롭**(drain ~7.9k 관측, 앞선 런 ~9.4k — 둘 다 10k 미만). 이는 순간 스톨이 아니라 **drain < 도착의 *지속 deficit***이고, **지속 deficit은 어떤 큐 크기로도 못 고친다**(큐는 변동을 흡수할 뿐 평균 부족을 못 메움). device-on의 정확한 무손실 ceiling(<10k)은 안 쟀지만, 10k에 못 닿는 것은 확정.
- → **append-only(device 분리)가 10k 무손실의 유일하게 확인된 경로이며, 분리는 *유익*이 아니라 *필수*다.** 정위치 = M4 Redis 최신상태 캐시. **핵심 대비**: 큐 흡수는 drain > 도착인 append-only에서만 통하고(순간 스톨만 타넘음), drain < 도착인 device-on에선 큐를 키워도 채워질 뿐이다.

## C. 무손실 10k — 드롭의 원인은 큐 용량
append-only N=16, 평탄 도착 10,000:

| 큐 capacity | dropped/s | p95 | 큐 피크 |
|---|---|---|---|
| 10,000(기본) | 버스트(~2,500/s) | 199ms | 10,000(참, 넘침) |
| **200,000** | **0** | (꼬리 있음) | ~11,000~12,000(흡수) |

- 드롭의 기전: 디스크가 ~100%인 상태에서 **PostgreSQL 체크포인트가 더티 페이지(랜덤 쓰기)를 flush할 때 1~2초 디스크 스톨**(쓰기 지연↑·IOPS↓, CPU·풀·GC는 정상 → 디스크측). 그 사이 워커 배수율이 도착 밑으로 떨어져 큐 backlog가 **~11,000~12,000**까지 쌓인다.
- 큐 10k는 이 backlog를 못 담아 넘쳐 드롭. **큐 200k는 흡수 → dropped/s=0.** 평균 배수율 ≥ 도착이므로 큐는 *순간 스톨*만 타넘으면 되고 스톨 사이 다시 빈다.
- 큐 사이징 = **견뎌야 할 worst 스톨 × 초당 유입 × 1.5~2배**(메모리 한도 내). worst는 측정값(~12k)으로 — 200k는 안전 여유(실제 ~32k면 충분).

## After — 종합
| 경로 | 처리율 | 병목 |
|---|---|---|
| device-on (현 정상 경로) | **drain < 10k** (@10k 도착 큐 200k가 가득 차고 드롭, drain ~7.9k 관측) | device 행 락(워커 스케일 차단) |
| append-only (M4 타깃 경로) | **10,000 무손실**(큐 200k) | 디스크(WAL+체크포인트) |
| append-only 과포화 천장 | ~14,400(N=16) | 디스크 순차 대역폭 |

## 해석
1. **워커 병렬화로 단일 워커 병목 해소**(group commit 스케일, ~14k까지).
2. **둘째 병목 = device 행 락**(핫패스 upsert) — append-only식 워커 스케일을 막는다(N=12: off 12.8k/디스크100% vs on 9k/디스크80%). device-on + 큐 200k @ 10k에서 **큐가 가득 차고 드롭**(drain < 도착, 지속 deficit) → **큐로는 못 고치며 device 분리(M4)가 10k에 필수**임이 측정으로 확정. (큐 흡수는 drain > 도착인 append-only에서만 통함.)
3. **드롭의 원인은 배치 큐 용량**이었다. 체크포인트 스톨의 backlog(~12k)를 기본 큐(10k)가 못 담아 넘친 것. 큐 200k 흡수로 **단일 5400rpm HDD에서 10,000 rows/s 무손실** 달성(SSD 없이, 내구성 안 풀고). 단, 큐가 클수록 크래시 시 유실 창이 커짐 — 내구 버퍼는 M4 Redis Streams 과제.
4. **SLO 10k**: append-only(=M4가 만들 경로)에서 무손실 달성으로 검증. 현 device-on 경로는 ~9k.

## 폐기한 시도 (정직 기록)
- **bgwriter 공격적 트리클**(`lru_maxpages 100→1000`, `delay 200→50ms`): 스톨을 *줄이려는* 시도였으나, 이미 포화된 단일 디스크에 랜덤 데이터파일 쓰기를 더해 순차 WAL fsync와 헤드 경쟁 → p95 3.5ms→199ms로 **악화**. 폐기. **단일 포화 디스크에선 스톨을 줄이는 config가 아니라 흡수하는 큐가 답.**
- **`checkpoint_timeout=15min`**: 부하 테스트가 5분이라 그 설정이면 테스트 창 안에서 timed 체크포인트가 발생하지 않음 → "드롭 0"이 스톨을 *제거*가 아니라 *관측 창 밖으로 밀어낸* 측정 함정. 실행 전 폐기. 검증 기준을 "테스트 중 체크포인트가 실제 발생(`pg_stat_bgwriter` 카운터 증가)했음에도 dropped/s=0"으로 교정.
- **잘못 짚은 병목 가설들**: CPU 과구독(CPU 77% 미포화로 기각) / N=8 "과병렬화"(노이즈 2점으로 곡선을 단정 — 실제 과병렬화는 N≥12에서 device 락) / 램프 피크 기반 조기 "SLO 달성" 선언(평탄 측정에서 device-on은 10k에 드롭으로 드러나 정정). 모두 평탄·격리 측정으로 정정.
