# 성능 병목 추적 — 측정으로 병목을 옮겨온 기록

실시간 디바이스 텔레메트리 시계열 파이프라인의 성능을 마일스톤별로 개선한 기록이다.
일하는 방식은 하나다: **병목을 측정으로 특정 → 해결 → 병목이 어디로 이동했는지 재측정.**
추측("느려질 것 같다")이 아니라 결정적 지표(deciding metric)로 병목을 인과 증명하고, 해결 뒤에는 반드시 다음 병목을 다시 측정한다.

모든 수치는 단일 측정 박스에서 나왔다: i7-6700HQ 4c/8t · 8GB · **5400rpm HDD**(단일 회전 디스크).
절대값은 이 디스크에 종속되므로, 아래 수치는 절대 성능이 아니라 **구조·쿼리 간 비율**로 읽는다.
상세 수치·해석·원본 데이터는 각 절 끝의 `measurements/Mx.md`에 있다.

## 병목 이동 지도

| 단계 | 병목 | 핵심 증거 | 해결 | 결과 | 이동한 다음 병목 |
|---|---|---|---|---|---|
| **① M0** 수집 baseline | HDD `fsync` | CPU 유휴 2~8% · 디스크 `%util` 97% · `f_await` 25ms · 계산 일치(40 fsync/s ÷ 1.2 fsync/req ≈ 33) | 단건 insert + 커밋마다 `fsync`(naive) | **33 req/s** | `fsync` 횟수 자체 |
| **② M1** 배치 적재 | `fsync` 횟수 | fsync/req 1.2 → 0.059 | 인메모리 큐 + 배치 워커 | **1,437 req/s (~44×)** | InnoDB B-tree 랜덤 위치 쓰기(data `fsync`) |
| **③ M2** 순차 저장 | 랜덤 위치 쓰기 | 디스크 평균 쓰기 200KB(순차) · 피크 59%(미포화) | TimescaleDB 하이퍼테이블(순차 append) | **5,459 rows/s (~3.8×)** | 단일 배치 워커(HikariCP active=1) |
| **④ M2-par** 워커 병렬화 | 단일 워커 + device 행 락 | N=6→12→16 처리량 스케일 · 데드락 재현 | 워커 N=16 + `TreeMap` 락 순서 + 큐 200k | **도착 10k rows/s 무손실** | 시간에 따른 DB 성장 |
| **⑤ M2-sustain** 지속 적재 | DB 성장(현재 청크 인덱스 > `shared_buffers`) | 디스크 읽기 ≈ 0(직접 증거) · 63분 편차 ±1% | 청크 7일 → **5분** + retention 12h | **지속 10k 평평, 드롭 0** | (읽기경로로 전환) |
| **⑥ M4a** 읽기경로 | 쿼리 복잡도(일 = O(전체 행)) | `EXPLAIN` loops=1M · external merge spill | 상관 서브쿼리 → **`LATERAL`**(O(디바이스)) | 8.65s → **35ms (~250×)**, 캐시 없이 | 응답 페이로드 425KB |
| **⑦ M4b** 실시간 | 적재 핫패스에 push가 얹힘 | A 데모에서 커넥션 풀 고갈 | Redis Streams fan-out(`storage`/`monitoring` 컨슈머 그룹) + WebSocket push | **지속 10k 무손실(워커4)·재시작 at-least-once** | Redis 버퍼(MAXLEN vs maxmemory) → storage 워커 → 디스크 |
| **⑧ M-MQTT** 수집 프로토콜 | 수집 어댑터 인입(단일 구독 콜백 스레드) | 같은 스토리지가 HTTP로는 9.7K를 디스크 65%로 처리 vs MQTT 3.25K에 디스크 90% · 배치 28행 · 커밋 102/s | 처리 오프로드(워커 8) + shared subscription(연결 4) | **3.25K → ~9K (2.8×)** | 브로커(mosquitto 단일 스레드) |
| **⑨ M-http-capacity** 인입 상한 | 박스 CPU | 코어 핀 6→8에 12K→16K 선형 확장(+33%) · 서버 처리시간 끝까지 ≤24ms · CPU 분해 JVM 44% > DB+OS 28% | (규명 단계 — 스레드·큐 락·Poller·스토리지는 반증) | 함대 상한 **12K(핀6) / 16K(핀8)** | 단일 부하 생성기 |
| **⑩ M-e2e-soak** 전 구간 소크 | (구간별 검증의 헤지) | 양끝 정산: k6 발신 38,616,836 ≈ 스트림 수신 38,617,038 · pending·lag·poison 0 | 전 구간 61분 유지 런 | **10k × 61분 무손실** | 단일 부하 생성기(서버는 p95 24ms·디스크 70%로 여유) |

한 줄로: **33(fsync) → 44× 배치 → 3.8× 순차 저장 → 10k 무손실 → 읽기 250× → 실시간 fan-out → MQTT 인입 2.8× → 인입 상한 = CPU(12K/16K) → 전 구간 61분 무손실.**
각 단계의 해결은 병목을 없앤 게 아니라 **다음 층으로 이동**시켰고, 그 이동을 다시 측정한 것이 이 문서의 골격이다.
⑧~⑩에서 병목은 처음으로 저장 계층 밖으로 나갔다 — 수집 어댑터, 브로커, 박스 CPU, 그리고 측정 장비 자신이다.
표 밖에 하나 더 있다: **◆ disk-baseline**(2026-07-07)은 **앞선 귀속을 검증·정정한 하드웨어 특성화**다. 병목을 옮긴 단계가 아니어서 표에는 넣지 않았다. ④가 "순차 대역폭 수렴"으로 적었던 한계의 실체는 durable sync 지연과 헤드 경합이었고(대역폭은 0.26%만 쓴다), 이를 `fio`로 가렸다.

## 방법: 결정적 지표로 인과를 증명한다

각 단계는 "무엇이 병목인가"를 가리키는 **하나의 결정적 지표**를 먼저 정하고, 그 지표가 움직일 때 최대 처리량(throughput)이 따라 움직이는지로 인과를 증명한다.
예를 들어 M1의 결정적 지표는 **요청당 `fsync` 횟수**(`Innodb_data_fsyncs` 델타 ÷ 요청 수)다.
이 값이 1.2에서 0.059로 줄자 최대 처리량이 44배 올랐다 — "병목 = fsync"가 상관이 아니라 인과임을 이 한 쌍의 움직임이 보인다.
지표를 정하지 않고 처리량만 보면 "빨라졌다"까지만 말할 수 있고, 왜 빨라졌는지는 증명하지 못한다.

## 단계별 기록

각 단계는 같은 틀로 정리한다: **상황**(무엇을 하고 있었나) · **병목**(무엇이 한계였나) · **원인**(측정으로 어떻게 규명했나) · **해결**(무엇을 바꿨나) · **결과**(수치) · **다음 병목**(어디로 이동했나).

### ① M0 — 수집 baseline

- **상황** — 가장 단순한 구현. 요청 한 건마다 행 하나를 insert하고 트랜잭션을 커밋한다.
- **병목** — 커밋마다 `fsync`가 걸린다. 5400rpm 단일 HDD에서 이 동기 쓰기가 최대 처리량을 **33 req/s**로 묶었다.
- **원인** — CPU 유휴 2~8%(계산이 병목 아님), HikariCP 커넥션 풀 대기, 디스크 `%util` 97%·`f_await` 25ms. 계산으로도 설명된다: 디스크 40 fsync/s ÷ 요청당 1.2 fsync ≈ 33.
- **결과** — baseline **33 req/s**(이후 모든 비교의 기준점).
- **다음 병목** — `fsync` 횟수 자체. 커밋을 모으면 요청당 `fsync`를 줄일 수 있다 → ②.

상세: [measurements/M0.md](measurements/M0.md)

### ② M1 — 배치 적재

- **상황** — baseline 33 req/s. 병목은 요청당 `fsync` 횟수.
- **병목** — 요청 1건마다 커밋 1회 → `fsync` 1회. 요청당 `fsync` 1.2회.
- **해결** — 수집 요청을 인메모리 큐에 넣고 배치 워커가 모아서 한 번에 insert·커밋한다(`JdbcTemplate.batchUpdate`). 요청 N건이 `fsync` 1회를 공유. 내구성 유지(`flush=1`).
- **결과** — fsync/req 1.2 → 0.059, 최대 처리량 **33 → 1,437 req/s(약 44배)**.
- **다음 병목** — 로그 `fsync`가 아닌 **data `fsync`**. InnoDB가 B-tree 인덱스 여러 페이지를 랜덤 위치에 갱신하는 쓰기가 남는다.

상세: [measurements/M1.md](measurements/M1.md)

### ③ M2 — 순차 저장 (TimescaleDB)

- **상황** — 배치로 커밋을 모았는데도 디스크가 다시 병목. 이번엔 랜덤 위치 쓰기.
- **병목** — InnoDB B-tree는 데이터를 여러 페이지의 랜덤 위치에 갱신한다. 회전 디스크에서 랜덤 위치 쓰기는 순차 쓰기보다 느리다.
- **해결** — 앱 전체를 MySQL에서 PostgreSQL/TimescaleDB로 교체하고, 텔레메트리를 하이퍼테이블에 시간순으로 append(순차 쓰기).
- **결과** — 최대 처리량 **1,437 → 5,459 rows/s(약 3.8배)**. 디스크 평균 쓰기 200KB(순차)·피크 59%로 포화에서 벗어남 = 랜덤→순차 전환의 직접 증거.
- **다음 병목** — 애플리케이션. 배치 워커가 하나뿐이라(HikariCP active=1) 여유가 생긴 디스크 대역폭을 다 쓰지 못한다.

상세: [measurements/M2.md](measurements/M2.md)

### ④ M2-par — 워커 병렬화

- **상황** — 디스크 사용률은 피크 59%에 그치는데 워커가 하나. 도착 목표는 10k rows/s.
- **병목 1** — 단일 워커가 디스크 순차 대역폭을 못 채운다.
- **해결 1** — 배치 워커를 1개 → N개로. 공유 큐를 나눠 drain, 워커당 커넥션 1개. 여러 커밋이 group commit으로 묶여 스케일한다(N=6 9.5k → N=12 12.8k → N=16 14.4k에서 평탄해짐). *이때는 이 평탄화를 "순차 대역폭에 수렴"으로 적었으나, 뒤의 하드웨어 특성화가 그 귀속을 정정했다 — 아래 ◆ disk-baseline.*
- **병목 2** — 매 요청이 device 행을 upsert하는데, 여러 워커가 같은 device 행 락을 다툰다. device 갱신 off면 N=12에서 12.8k(디스크 100%), on이면 9k(디스크 80%). 게다가 도착 순서대로 락을 잡다 `deadlock detected`.
- **해결 2** — device_id를 정렬해(`TreeMap`) 모든 워커가 같은 순서로 락을 잡게 함(데드락 제거). 큐를 200k로 잡아 체크포인트가 drain을 멈출 때의 backlog(약 12k)를 흡수.
- **결과** — append-only N=16 + 큐 200k로 **도착 10k rows/s에서 드롭 0**, 내구성 유지, 단일 5400rpm HDD.
- **다음 병목** — 시간에 따른 DB 성장. 그리고 device 갱신이 적재를 막는다는 이 측정이 device 상태를 적재 경로에서 분리하는 M4의 근거가 됐다.

상세: [measurements/M2-par.md](measurements/M2-par.md)

### ⑤ M2-sustain — 지속 적재

- **상황** — M2-par는 매 런마다 테이블을 비워(`TRUNCATE`) 순간 용량을 쟀다. 실제 운영은 시간이 지나며 DB가 커진다.
- **병목** — 통제 없이 오래 적재하면 처리량이 13k에서 10k 밑으로 떨어진다. 원인은 DB 성장이다: 기본 청크가 7일이라 10k/s에서 현재 청크가 수십억 행으로 커지고, 그 청크의 인덱스가 `shared_buffers`(2GB)를 넘으면 insert마다 인덱스 페이지를 디스크에서 읽어야 해 drain이 도착률 밑으로 떨어진다.
- **해결** — 청크를 7일 → **5분**으로 줄여 현재 청크(약 300만 행)의 인덱스를 `shared_buffers` 안에 유지. 디스크 총량은 retention 12h로 묶음(약 133GiB, 디스크 38%).
- **결과** — 63분간 도착 10k가 평평(편차 ±1%, 드롭 0). 순수 insert 워크로드의 디스크 읽기가 거의 0 = 인덱스가 캐시에 있다는 직접 증거.
- **폐기한 시도** — 백그라운드 압축. 결과물은 7,177MB → 177MB(40.56배)로 좋지만, 과정의 I/O가 문제였다. 1시간 지난 청크는 캐시에 없어 압축이 디스크를 읽어야 하고(0 → 11 MB/s), 쓰기만으로 이미 88%인 단일 HDD가 95%+로 포화하며 flush가 105ms → 700ms로 늘어 27분간 5,858,290행을 드롭했다. M2-par의 bgwriter와 같은 결과 — 포화한 단일 HDD에 경쟁 I/O를 더하면 drain의 I/O를 빼앗는다. 결론: 단일 HDD에선 지속 무손실 10k와 백그라운드 압축이 양립 불가 → raw 적재 + retention drop(압축은 전용 디스크 생기면 재도입).

상세: [measurements/M2-sustain.md](measurements/M2-sustain.md)

### ⑥ M4a — 읽기경로 쿼리

- **상황** — 여기서 병목은 디스크가 아니라 쿼리 방식. 관제 지도의 "디바이스별 최신 1건"(`GET /api/telemetry/latest`)을 M0은 상관 서브쿼리로 짰다.
- **병목** — 서브쿼리가 행마다 재실행된다(`EXPLAIN` loops=1,000,000). 결과는 디바이스 수(1,000)뿐인데 일은 전체 행 수(100만)에 비례 → 100만 행에서 단일 조회 8.7s.
- **해결** — 같은 조회를 세 방식으로 짜 비교하고 `LATERAL`을 택했다.

  | 쿼리 | 접근 | @1M행 | @10M행 |
  |---|---|---|---|
  | ① 상관 서브쿼리 | 행마다 "이 디바이스의 최신인가" 재확인 | 8,748 ms | — |
  | ② `DISTINCT ON` | 전체를 정렬해 device별 첫 행 | 813 ms | 24분 |
  | ③ `LATERAL` | device 목록으로 시작, device당 PK 인덱스 1회 | — | 웜 406 ms |

  ②는 최신만 필요해도 전체 행을 정렬해, `shared_buffers`를 넘으면(10M ≈ 3GB) 디스크 정렬(external merge)로 24분까지 급락한다. ③은 `device.org_id`로 device를 좁힌 뒤 device당 PK 인덱스(`device_id, recorded_at`)로 최신 1행만 집어 일을 결과 크기 O(디바이스)에 맞춘다.
- **결과** — 엔드포인트 지연 상관 서브쿼리 대비 **약 250배**(k6 VUS=1 p95 8.65s → 35ms), 캐시 없이 쿼리 개선만으로.
- **다음 병목** — 쿼리가 아니라 응답 크기. 조회 응답이 약 425KB(디바이스 1,000 × 풀 텔레메트리)라 지도가 그리는 필드만 담는 경량 렌더셋이 다음 개선 대상. (Redis 캐시 `LatestStateLookup` 포트는 코드는 있으나 쿼리 ③으로 충분해 기본값 DB로 껐다 — 캐시의 역할은 M4b push의 접속 시 스냅샷 소스에서.)

상세: [measurements/M4a.md](measurements/M4a.md)

### ⑦ M4b — 실시간 fan-out (Redis Streams)

- **상황** — 읽기경로 마지막 조각. 관제 지도를 폴링에서 push로 전환.
- **병목** — 초기 데모(A)에서 적재 핫패스에 WebSocket push를 직접 얹었더니 커넥션 풀이 고갈됐다. 적재와 push가 같은 경로를 다툰다.
- **해결** — 인메모리 큐를 Redis Streams로 바꾸고 독립 컨슈머 그룹 둘로 분리. `storage` 그룹은 배치 적재(적재 후 `XACK`, `ON CONFLICT`로 멱등), `monitoring` 그룹은 최신부터 읽어 WebSocket push. 각 그룹이 커서를 따로 가져 push가 적재를 막지 않는다.
- **결과** — 박스 측정에서 **병목이 세 번 이동**했다. (1) **Redis 버퍼**: `MAXLEN` 기본 1M이 `maxmemory` 256mb보다 커(1M×0.5KB≈512MB) 트리밍이 못 걸려 OOM — 스트림은 append-only 로그라 `XACK`해도 엔트리가 안 지워진다. `MAXLEN`을 메모리 예산에서 역산해 bound. (2) **storage 워커**: 1→2→4로 늘리자 유실 34.5→13.7→0%, 디스크 %util 37→90→95%로 병목이 애플리케이션에서 디스크로 이동. (3) **디스크**: 워커 4로 **지속 10k 무손실**(디스크 60% 여유). 초과 부하는 유실이 아니라 admission 백프레셔(intake 지연↑ + 생성기 drop). **재시작**은 부하 중 `kill -9` 후 `DB=202성공수`·`pending→0`으로 **무손실·무중복**(at-least-once + 멱등) 실증. 결정적 세부: **버퍼는 worst-case 컨슈머 랙보다 커야**(트림은 oldest부터) — `MAXLEN 200K`는 warm-up lag 스파이크에 0.037% 유실, 400K는 0%.
- **측정 위생 교훈** — 짧은 부하 런은 warm-up 트랜지언트를 정상상태로 오인한다. 90s 런은 10k에서 6k만 delivered했으나, 5분 런은 정상상태에서 flat 10k를 유지했다.

### ⑧ M-MQTT — 수집 프로토콜 확장 (MQTT)

- **상황** — IoT 표준 전송인 MQTT를 수집 경로에 추가했다. 어댑터가 브로커를 구독해 역직렬화·검증한 뒤 HTTP와 같은 `TelemetryIngestService`로 합류한다(core 변경 0). 하류를 변수에서 빼려고 `mode=stream`으로 고정했다 — 그 구간은 ⑦이 이미 지속 10k 무손실로 특성화했으므로 남는 변수는 인입 계층 하나다.
- **병목** — 단일 Paho 콜백 스레드. `messageArrived`가 역직렬화·검증·`XADD`를 한 스레드에서 직렬 처리해 인입이 **3.25K msg/s**에 묶였다.
- **원인** — 여기서 디스크 지표가 함정이었다. MQTT 3.25K일 때 디스크 `%util`이 90~96%라 스토리지 한계처럼 보였지만, **같은 날 같은 스토리지가 HTTP로는 9.7K를 디스크 65%로 처리했다**(대조군). 낮은 인입에서는 `XREADGROUP`이 있는 만큼 즉시 반환해 배치가 28행밖에 안 차고, 그만큼 커밋이 초당 102회로 늘어 5400rpm HDD의 fsync 한계에 부딪힌다. 디스크 포화는 저인입의 **증상**이지 원인이 아니었다. `maxDelayMs`를 200→1000으로 5배 늘려도 인입·배치·디스크가 그대로인 것이 이를 확인한다(배치 크기를 정하는 것은 블록 타임아웃이 아닌 인입 속도다).
- **해결** — 인입을 두 축으로 병렬화하고 각각 한 변수만 바꿔 대조했다. 처리 병렬화(콜백 → 바운드 익스큐터 오프로드, 매뉴얼 ack로 at-least-once 유지)로 3.25K→7.4K, 수신 병렬화(연결 1→4, shared subscription `$share/{group}/telemetry/+`)로 7.4K→~9K.
- **결과** — **3.25K → ~9K(2.8배)**, HTTP 경로의 스토리지 처리량에 근접. 인과가 매 단계 따라 움직였다: 인입↑ → 배치 28→156→388행 → 커밋 102→48→24/s → fsync↓ → 디스크 90→80%. **처리량이 2.8배인데 디스크 사용률은 오히려 내려간 것**이 "디스크 포화 = 저인입 증상"이라는 진단의 증명이다.
- **다음 병목** — 브로커. 부하를 20K로 올리면 연결 수와 무관하게(conn4·conn8 둘 다) 4K대로 붕괴하고 브로커 드롭이 초당 16K로 뛴다. offer 10K에서는 conn8이 9.8K를 정상 처리하므로 앱이 아니라 **mosquitto 단일 스레드의 혼잡 붕괴**다. 10K 초과는 브로커 스케일(EMQX·HiveMQ 등)의 영역이고, 이 지점이 ADR 0004가 예고한 구현체 교체 게이트다.

상세: [measurements/M-MQTT.md](measurements/M-MQTT.md) · 원본 [M-MQTT-raw/](measurements/M-MQTT-raw/)

### ◆ disk-baseline — 하드웨어 기준선 (진단 사슬 정정)

**앞선 진단을 검증한 하드웨어 특성화**다. "적재 한계가 디스크 대역폭인가"를 앱·DB를 빼고 `fio`로 디스크만 때려 확인했다. 병목을 옮긴 단계가 아니어서 번호 대신 ◆를 붙였다.

- **결론 — 병목은 대역폭이 아니라 durable sync 지연이다.** 같은 디스크가 접근 패턴에 따라 세 자릿수로 갈린다: 순차 쓰기 61.7 MB/s vs durable 쓰기(매 쓰기 `fdatasync`) 0.16 MB/s. 차이는 sync 하나뿐이고, **durable 경로가 쓰는 대역폭은 전체의 0.26%**다. 대역폭은 비어 있고 한계는 초당 약 20회의 durable sync(건당 50ms)라는 회전판 물리다.
- **`%util`은 포화 지표로 못 쓴다.** ①과 ③이 같은 99% util인데 대역폭은 380배 차이다. `%util`은 장치가 바빴던 시간 비율일 뿐이라, 이 값만으로 "디스크가 한계"라고 읽으면 안 된다 — ⑧에서 디스크 90%를 스토리지 한계로 오인한 것과 같은 함정이다.
- **적재 처리량이 이 물리에서 나오는 방식** — `처리량 = 초당 durable sync 횟수(약 20, 고정) × sync당 행 수(배치가 키우는 값)`. naive는 20×1 ≈ 20 rows/s, 배치 500이면 20×500 ≈ 10,000 rows/s. ②의 44배가 이 곱셈이다. 앞항(초당 sync 횟수)은 회전판 물리라 고정이므로, 앱이 키울 수 있는 항은 **배치 크기** 하나다. 남는 99.7% 대역폭은 그렇게 꺼내 쓴다.
- **④의 귀속 정정** — N=16의 평탄화는 순차 대역폭 수렴이 아니었다. 실제로는 체크포인트의 랜덤 쓰기(회전지연 바운드, 169 IOPS)가 순차 WAL과 **단일 헤드를 경합**해 생긴 한계다. M2-par에서 bgwriter 트리클을 넣자 배치 지연이 3.5ms에서 199ms로 뛴 것이 이 헤드 경합의 실증이다.
- **진단 사슬** — M2-par(대역폭으로 귀속) → disk-baseline(sync 지연·헤드 경합으로 정정) → ⑨ M-http-capacity(배치 운영점에서는 박스 CPU). 세 단계를 거치며 같은 현상의 원인이 두 번 바뀌었다. 각 정정은 앞 기록을 지우지 않고 그대로 남겨 뒀다.
- **함의의 범위** — "SSD가 유일한 큰 레버"는 **fsync 바운드인 naive 경로에 한정**이다. 배치된 운영점의 12~16K 한계는 CPU라 SSD로 안 올라간다. 하드웨어 기준선 하나를 전 구간에 일반화하지 않도록 이 조건을 명시한다.

상세: [measurements/disk-baseline.md](measurements/disk-baseline.md)

### ⑨ M-http-capacity — HTTP 인입 상한 (CPU 바운드 규명)

- **상황** — ⑧이 HTTP 상한을 "부하도구 한계 또는 스토리지 ~9.7K"로 귀속했는데, 그 귀속이 부정확했다. 그래서 이 단계의 산출은 처리량 개선이 아닌 **귀속 정정과 병목 규명**이다.
- **부하 모델부터 교체** — 기존 스크립트는 총 도착률만 통제하고 deviceId를 회전시켜, 디바이스별 주기와 연결이 통제되지 않았다. "1Hz 디바이스 N대"를 재현하지 못하므로 MQTT 벤치(클라이언트 1 = 디바이스 1)와 비교가 안 된다. `telemetry-fleet.js`로 **1 VU = 디바이스 1대**가 고정 deviceId·지속 커넥션으로 매초 1건을 보내게 바꿨다. 서버가 느려지면 실제 단말처럼 1Hz에서 밀리고, 그 밀림이 지표로 잡힌다.
- **병목** — 박스 CPU. 요청당 앱 처리 비용(JSON 역직렬화 + 검증 + 봉투→도메인 매핑 + enqueue)이 지배분이다.
- **원인** — **코어 핀을 6개에서 8개로 늘리자 함대 상한이 12K에서 16K로 정확히 비례해 올랐다(+33% → +33%). 선형 확장이 CPU 바운드의 증거다.** 뒷받침: 서버 처리시간이 붕괴 구간까지도 24ms 이하로 낮았다(느려서 못 받은 게 아니라 CPU가 동나 못 받았다), CPU 분해에서 JVM 44%가 DB+OS 28%보다 크다, 스토리지는 디스크 68%·HikariCP pending 0으로 여유다.
- **반증 기록** — 다른 후보를 하나씩 지웠다. Tomcat 워커 스레드(300→600에 처리량 무변, 지연만 22→50ms 악화, 스레드 덤프상 워커는 큐에서 대기), 인입 큐 락(consumer 여력 11.7K rows/s > 달성 인입, 드롭 0), Poller 단일코어(코어별 사용률이 78~90%로 균등).
- **결과** — 함대 상한 **12K(핀6) / 16K(핀8)**, 요청당 앱 CPU **약 0.25~0.3ms**. ⑧의 HTTP 귀속을 정정한다 — 그때의 "~10K"는 단일 고부하 스텝이 부하 머신을 즉시 포화시켜 나온 **붕괴값**이었고 박스의 실제 상한은 더 높다.
- **다음 병목** — 단일 부하 생성기. 16K 위에서는 맥이 먼저 포화한다(sys 74%, idle 0~4%). 하드웨어를 늘리지 않고 이 상한을 올리려면 남은 지렛대는 앱 핫패스의 CPU 절감뿐이다.
- **비교 주의** — 핀 해제(0–7)는 다른 마일스톤(전부 0–5 핀)과 조건이 다르다. CPU 바운드를 확증하기 위한 별도 라벨 실험으로만 유효하다.

상세: [measurements/M-http-capacity.md](measurements/M-http-capacity.md)

### ⑩ M-e2e-soak — 전 구간 통합 소크

- **상황** — 그때까지 저장 계층(63분)·스트림 fan-out·MQTT 수집을 **각각 따로** 특성화했을 뿐, HTTP → Redis Streams → TimescaleDB 전 구간을 한 번에 60분 넘게 돌린 적이 없었다. 이 런은 "저장은 63분, 나머지는 각각 별도"라는 조건부 서술을 지우기 위한 것이다.
- **결과 — 61분 유지 구간에서 유실 0.** 양끝에서 정산했다: k6 발신 **38,616,836**건 ≈ Redis 스트림 수신 **38,617,038**건(차 202건, 0.0005%), 여기에 storage 컨슈머의 pending 0 · lag 0 · poison 0 · flush 에러 0. 컨슈머가 적재 성공 후에만 `XACK`하므로 pending 0은 읽은 전량이 DB에 들어갔다는 뜻이고, lag 0은 안 읽은 엔트리가 없다는 뜻이다. 이 구간 서버 p95 24ms · 디스크 70% · HikariCP pending 0.
- **지속 한계는 파이프라인이 아니라 부하 생성기** — 지속 처리량이 10k를 조금 못 미친(~9.8k) 이유를 네 단계로 규명했다. (1) 진단 런에서 워커 스레드가 300에 붙었다. Little 법칙이 예측하는 동시 처리수와 같은 값이다(9,983 × 0.030s ≈ 300) — 풀 크기가 수요와 맞아떨어진 것이지 대기가 쌓인 신호는 아니다. (2) 별도 clean 런은 같은 디스크 사용률에서 10,000/s로 평평했다 — 9.7k를 한계로 본 해석을 반증. (3) 처리량이 9,979→9,481로 떨어지는 내내 서버는 p95 22ms · GC 0 · 디스크 70%로 전부 정상이었다. 닫힌 루프에서 서버가 빠른데 처리량이 떨어지면 요청이 도착하지 않는 것이다. (4) 맥을 직접 보니 load average 11.47(논리 코어 10 초과) · sys 35% · 여유 램 76MB로 포화 상태였다. 모니터링 스택까지 같은 맥에서 돌린 것이 겹쳤다.
- **폐기한 시도 — 가상 스레드.** "스레드풀 300이 상한이니 없애면 오른다"는 가설을 측정으로 기각했다. 처리량 8,036/s로 떨어지고 서버 p95가 726ms로 25배 늘었다. 그런데 XADD on-wire 3~8ms · 앱 CPU 0.3 · 디스크 35% · HikariCP 0으로 **자원은 전부 유휴인데 요청 wall-clock만 폭증했다** — 처리 능력이 고정된 공유 직렬화 지점에 큐가 쌓였다는 신호다. 바운드 풀이 사실상 그 큐를 얕게 유지하는 admission control이었다. 직렬화 지점이 Lettuce 단일 연결인지 핫패스의 락인지는 프로파일링이 필요해 단정하지 않는다.
- **남은 것** — 지속 한계가 측정 장비 쪽이라 **파이프라인의 실제 한계는 아직 미측정**이다(서버 여유: p95 24ms · 디스크 70%). 부하 머신을 늘리거나 모니터링 스택을 분리한 뒤에야 잴 수 있다. 또한 닫힌 루프 1Hz 페이싱은 도착을 매끄럽게 만들므로 이 소크는 실제 함대의 상관된 버스트(재접속·리트라이)를 포함하지 않은 best-case에 가깝다.

상세: [measurements/M-e2e-soak.md](measurements/M-e2e-soak.md)

## 관통하는 원칙

- **병목은 사라지지 않고 이동한다.** 각 단계의 해결은 병목을 다음 층으로 옮겼다(디스크 fsync → fsync 횟수 → 랜덤 위치 쓰기 → 단일 워커 → device 락 → DB 성장 → 쿼리 복잡도 → 응답 크기 → 수집 어댑터 인입 → 브로커 → 박스 CPU → 부하 생성기). 계단식 이동을 매번 재측정하는 것이 이 프로젝트의 방식이다. 뒤쪽 단계에서 병목이 저장 계층 밖으로 나간 뒤에는 **측정 장비 자신이 한계가 되는 구간**이 생겼고, 그것을 서버 한계로 착각하지 않으려면 양쪽(SUT와 부하 머신)을 같이 봐야 했다.
- **결정적 지표로 인과를 증명한다.** 처리량만 보면 "빨라졌다"까지고, 지표(fsync/req, 디스크 읽기량, `EXPLAIN` loops, `accepted−DB` 유실, `XLEN` vs `MAXLEN`, 코어 핀 대비 처리량)가 함께 움직여야 왜 빨라졌는지가 증명된다. 잘못 해석한 사례도 기록했다 — M2의 k6 타임스탬프 미래 표류를 서버 붕괴로 잘못 해석한 일, M2-par에서 램프 피크를 SLO 달성으로 조기 선언한 일, M4b에서 90s 런의 warm-up 트랜지언트(6k)를 지속 최대 처리량으로 잘못 읽었다가 5분 런(정상상태 10k)으로 바로잡은 일, M-MQTT에서 디스크 90%를 스토리지 한계로 읽었다가 대조군으로 저인입의 증상임을 가린 일, M-e2e-soak에서 9.7k를 디스크·DB 신선도에 귀속했다가 부하 머신 포화로 정정한 일.
- **하나의 값은 병목을 못 가른다. 대조군이 가른다.** M-MQTT의 디스크 96%는 그 자체로는 스토리지 한계로도 읽힌다. 같은 날 같은 스토리지가 HTTP로 9.7K를 65%에 처리한다는 대조군이 있어야 인입과 스토리지가 갈렸다. 같은 이유로 M-http-capacity는 코어 핀만 바꾼 대조(6 vs 8), M-e2e-soak는 SUT와 부하 머신 양쪽 관측으로 판정했다.
- **폐기한 시도도 근거로 남긴다.** 단일 HDD에 경쟁 I/O를 더하는 시도(M2-par bgwriter 트리클, M2-sustain 백그라운드 압축)는 같은 이유로 무손실 적재를 깼다. 가상 스레드(M-e2e-soak)는 처리량을 떨어뜨리고 지연을 25배로 늘렸는데, 그 실패가 바운드 스레드풀이 admission control 역할을 하고 있었다는 사실을 드러냈다. 효과 없던 시도를 지우지 않고 남겨야 다음 판단의 근거가 된다.
